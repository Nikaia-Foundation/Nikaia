Nikaia · Very safe

What Nikaia checks

Many bugs follow patterns. Nikaia checks for those patterns before they reach your users.

Some problems can be ruled out while your program is being built. Others depend on what happens at runtime or on information the compiler cannot see. Here are five kinds of mistakes Nikaia helps you catch, and what its checks can guarantee.

1 Conflicting actions

The problem
When tasks interfere with each other, results can go wrong.
An example
Two tasks update the same account balance. One update can overwrite the other, and money appears to disappear.
What Nikaia checks
Nikaia restricts how tasks access and change shared data. A task that changes a value the other tasks also use is rejected when the program is built, with the way out named: give each task a value of its own, or keep the value in shared state that is changed through a lock.
The limit
Code outside Nikaia can create its own threads. When Nikaia cannot establish the necessary guarantees, you provide a safe boundary, such as passing a copy instead of shared data. The rules reject unsafe constructions; they are not a proof that every conceivable race is found.
Show the program and what Nikaia says 
use std::task

fn main() throws {
    let mut balance = 100
    task::scope fn(s) {
        s.spawn fn { balance = balance + 50 }
        s.spawn fn { balance = balance - 30 }
    }
    println(f"{balance}")
}

$ nikaia check main.nika
error[NK2107]: You're changing `balance` in a task of `task::scope`, and the scope's tasks all share `balance`.
  --> main.nika:6:22
   |
 6 |         s.spawn fn { balance = balance + 50 }
   |                      ^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: A scope's tasks run at the same time, each on a core of its own, so they would write `balance` at once.
   = help: Give each task a value of its own and combine them after the scope, or keep `balance` in a `SharedMut` and change it through `update`.

2 Tasks that get stuck

The problem
Sometimes tasks wait for each other forever.
An example
Two account transfers each hold a lock the other needs. Neither can continue.
What Nikaia checks
A task that pauses while it holds a lock is rejected, since everyone who needs that value would wait too. For several locks at once, update_all takes them in one fixed order, so two transfers cannot hold one each and wait for the other.
The limit
Nikaia does not yet reject a lock taken inside another lock when you write it by hand, so using update_all for several locks is up to you. And not every possible deadlock can be ruled out in every situation; where the analysis cannot decide, it does not claim the problem is solved.
Show the program and what Nikaia says 
use std::time

struct Account {
    balance: i64,
}

fn main() throws {
    let a = SharedMut(Account { balance: 100 })
    a.update fn(mut acc) {
        acc.balance -= 30
        time::sleep(5.millis())
    }
}

$ nikaia check main.nika
error[NK2202]: `time::sleep` can pause, but you're holding a lock here.
   --> main.nika:11:9
    |
 11 |         time::sleep(5.millis())
    |         ^^^^^^^^^^^^^^^^^^^^^^^
    |
    = note: While the lock is held, every other task that needs the value waits, so a pause here makes all of them wait too.
    = help: Call `time::sleep` before taking the lock and pass its value in, or after it with what the block returned.

Moving money between two accounts takes both locks at once, always in the same order:

update_all(a, b) fn(mut from, mut to) {
    from.balance -= 30
    to.balance += 30
}

3 Tasks that use too much memory

The problem
One task should not be able to consume unlimited memory.
An example
A task processes a large file and exhausts the memory available to it.
What Nikaia checks
A calculation that runs while the program is built has a limit on its steps and its memory, and stops with a message when it passes them. The language is specified so that each task at run time gets a memory budget of its own, and a task that exceeds it stops without taking the rest of the program down.
The limit
This is a protection, not a proof. Nikaia does not prove at build time that a task stays within its budget, and the run-time budget is not yet part of what the toolchain enforces.

4 Errors that go unhandled

The problem
When something fails, the program needs a way to deal with it.
An example
A program reads its configuration file. The file is missing, but the calling code assumes the read succeeded.
What Nikaia checks
Functions declare when they can fail, and what they can fail with is worked out from their bodies. A function that calls something that can fail, and neither declares it nor handles it, is rejected when the program is built.
The limit
For functions from outside Nikaia that nothing describes, Nikaia cannot know every way they fail. A description of the library closes that gap. The check shows where failures are not accounted for; it does not make the handling itself correct.
Show the program and what Nikaia says 
use std::fs

fn load() -> String {
    return fs::read_to_string("config.txt", fs::Root::Anywhere)
}

fn main() {
    println(load())
}

$ nikaia check main.nika
error[NK2605]: This function can fail, because `fs::read_to_string` can fail.
  --> main.nika:4:5
   |
 4 |     return fs::read_to_string("config.txt", fs::Root::Anywhere)
   |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: `fs::read_to_string` can fail with `io::IoError`.
   = note: A call that can fail looks like any other call, so its failure passes straight through this function unless you handle it.
   = help: Add `throws` to `load`, or handle it at the call: `… catch { … }`.

5 Broken promises

The problem
Every part of a program should be able to rely on what the other parts promise.
An example
A function expects a percentage between 0 and 100 but is called with 140.
What Nikaia checks
You write the expectation as an assert and it becomes a contract. A call that breaks it is rejected when the program is built, a promise about a result is available to the callers, and a contract carries across package boundaries.
The limit
A compiler cannot know whether data from files, arguments or the network is valid. Check it where it enters the program; once checked, the rest of the code can rely on it.
Show the program and what Nikaia says 
fn percent(n: int) -> int {
    assert(n >= 0 && n <= 100)
    return n
}

fn main() {
    println(f"{percent(140)}")
}

$ nikaia check main.nika
error[NK1207]: This call breaks `percent`'s precondition `n >= 0 && n <= 100` every time it is reached.
  --> main.nika:7:5
   |
 7 |     println(f"{percent(140)}")
   |     ^^^^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: Here `n` is 140.
   = help: Pass `percent` arguments for which `n >= 0 && n <= 100` holds, or check them with a guard before the call.

For data from outside, check it where it arrives. After the guard, the claim is proved:

let out = process::run("git", ["rev-parse", "HEAD"])
let n: int = out.stdout.len()
if n != 41 {
    println("not a commit id")
    return
}
assert(n == 41)     // proved: the guard above handled the other case
