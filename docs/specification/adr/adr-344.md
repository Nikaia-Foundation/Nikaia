# ADR-344: `json` Reads Into the Type the Caller Names, by the Database's Rules; a Schema Is a Build-Time Input; `json::Value` Is the Way Out for Text of Unknown Shape

**Status:** Accepted (D4's spelling of the opt-in is a proposal the owner has not confirmed)
**Date:** October 13, 2026 (#604)
**Answers:** what the official package `json` offers, where it lives, how a
text is read into a declared struct, what a JSON Schema does at build time,
and what reads JSON whose shape no struct describes
**Related:**
[ADR-338](adr-338.md) D2, D3, D5 (formats are official packages, read and write);
[ADR-299](adr-299.md) D3, D15-D19 (a database row is the struct the block names, matched by name);
[ADR-331](adr-331.md) (`@json::Name`, attributes read through `T::fields`);
[ADR-330](adr-330.md) (a type passed where the parameter list holds one);
Part II 10.3 (generating code from a type's shape), Part III 17.2, 17.3

## 1. Question

**What does `json` look like to a program, and how does a text become a
value of a type the program declared?**

ADR-338 made JSON an official package and said it reads and writes. It did
not say where the package's source lives, what a read returns, which mistakes
are found while the program is built and which while it runs, nor what a
program does with JSON whose shape it does not know (an LSIF dump, a
debugging aid).

## 2. How others do it

| Language / tool | Its answer | What it costs there |
| :--- | :--- | :--- |
| Rust, serde | `#[derive(Deserialize)]` writes a decoder per type at compile time; `serde_json::from_str::<T>`; unknown fields ignored unless `#[serde(deny_unknown_fields)]`; `serde_json::Value` for the rest | a derive on every type, a macro system; ignoring unknown fields hides a renamed field |
| Go, `encoding/json` | `json.Unmarshal(data, &v)` walks the struct by reflection at run time; tags `json:"x"`; unknown fields ignored unless `Decoder.DisallowUnknownFields`; `interface{}` / `map[string]any` for the rest | reflection at every call; a missing field is silently the zero value |
| Swift, `Codable` | the compiler synthesizes `init(from:)` per type; `JSONDecoder().decode(T.self, from:)`; a missing non-optional key throws, `null` only into an optional; unknown keys ignored | a conformance on every type; no dynamic tree in the standard library |

All three generate or find the decoder from the type; only Swift is as strict
about missing fields and `null` as ADR-299 D17/D18 are; none is strict about
unknown fields by default.

## 3. Facts that bear on it

* Reading a type's shape at build time exists (Part II 10.3): a loop over
  `T::fields` is unrolled per type, `.name`, `.ty`, `.of(value)` and
  `.attribute(X)` work, so `write[T]` can be written in Nikaia today.
  Tried with `target/release/nikaia run` on 2026-10-13: `describe[T: Struct]`
  unrolls; a `String?` field then reaches the backend as a Rust `Display`
  error rather than a Nikaia diagnostic.
* **Building** a value from its fields does not exist: a reflected field has
  no `.set`, and nothing makes a `T` from field values (`field.set(v, …)` is
  `NK1180`). A type passed as a parameter (ADR-330, `schema(CreateUser)`) is
  not parsed yet. Both are what `read[T]` needs and are D3's prerequisites.
* A package depended on by path works today; a grammar exported by a package
  (#520) and a `dsl` block naming it (#485) do not, nor does ADR-338 D3's
  `use` that takes an official package in by itself.
* The facts tool (`crates/rs2nika/facts`) reads LSIF with a hand-written
  reader (#579): the first program in this repository that needs JSON of a
  shape it does not declare up front.

## 4. Decision

### D1 — Official packages live in `packages/<name>/`, and a change there raises only that package's version.

`json` is `packages/json/`, a package like any other with its own
`nikaia.toml` and version. A change there does not move the language's
version; only the specification text that describes it does.

### D2 — First a plain package, taken in by a path dependency.

The first `json` exports functions and types only: no grammar export, and no
`use` that takes it in by itself. A program names it in `[dependencies]` by
path. ADR-338 D3 and the grammar export (#520, #485) are added later and
change no program that already compiles.

### D3 — `json::read[T](text)` reads into the type the caller names; the decoder is written while the program is built.

```nika
struct Contact { name: String, email: String? }
let c = json::read[Contact](text)                 // a Contact, or a thrown json::Error
let s = json::write(c)                            // write[T], T inferred
```

A call, not a `dsl` block: the text arrives while the program runs, and there
is nothing to check at the call but the type. The decoder for `T` is generated
from `T::fields` while the program is built, one per type a call names; no
reflection happens at run time. A failure throws `json::Error`, which carries
the line, the column and the path of the value (`$.contacts[3].email`).

### D4 — Mapping follows ADR-299 D16-D18.

A member matches the field of its name (or the name `@json::Name` gives,
ADR-331), never by position. Every field takes exactly one member: a member
given twice is an error, a field with no member is an error (D17's default). *Proposal, not
confirmed:* a missing member goes into a `T?` field as `null`, because JSON
writers commonly leave out what is `null`; the strict alternative is
`missing_fields: true` at the call, as D17 has it. `null` goes only into a `T?`. A
member with no field is an error unless the type allows it.

*Proposal, not confirmed by the owner:* the opt-in is an attribute on the
struct, `@json::Open` - unknown members are skipped for that type and only
that type, not its nested structs. A struct that wants to keep them declares
one field of type `Map[String, json::Value]` marked `@json::Rest`, which then
receives them. The reason for an attribute rather than a call option: it is a
property of the wire format the type describes, and every read of that type
should agree.

### D5 — A field's type is one JSON can be.

`bool`, the integer and float types, `String`, a `T?` of one, a `Vec[T]` of
one, a `Map[String, T]`, a declared struct (an object) or enum, and `json::Value`. Any other field type is refused at the call with
`NK1250`, naming the field and the path to it.

### D6 — A JSON Schema may be read while the program is built, and `T` is checked against it.

```nika
comptime SCHEMA = asset("contact.schema.json")
let c = json::read[Contact](text; schema: SCHEMA)
```

As ADR-299 D3: the schema is a file in the repository, read through `asset`.
The compiler checks `T` against it by D4's rules - a required property `T`
lacks, a field the schema does not have (unless `additionalProperties`
allows it), a type that does not match, a `T` field for a property that may be
`null` - and refuses the call with `NK1251`, naming the property and the
field.

**Not decided here:** run-time checks of the schema's constraints
(`pattern`, `minLength`, `minimum`, `enum` …). Nothing in this repository
needs them yet, and they raise questions this record cannot settle without a
user: whether they cost every read, whether a value's type should carry them
(a refinement type) instead of the call, and which drafts' regular
expressions apply.

### D7 — `json::Value` reads JSON of any shape.

```nika
enum Value { Null, Bool(bool), Int(i64), Float(f64), Text(String), List(Vec[Value]), Object(Map[String, Value]) }
let v = json::parse(text)                          // a json::Value
```

A number without a fraction or an exponent that fits an `i64` is `Int`,
otherwise `Float`. An object keeps its members in the order of the text.
`read[json::Value]` is the same as `parse`.

### D8 — `json::write[T](value)` writes the text (ADR-338 D5).

Fields in declared order, the names D4 reads, a `T?` that is `null` written as
`null`. Writing from a `Value` writes it as it is.

## 5. Rejected alternatives

* **Only the dynamic form** (`Value` and nothing typed): every program walks
  a tree by hand and finds a renamed member when it runs; it is what the
  facts tool does today (#579) and what this record wants to end.
* **A `dsl` block** (`dsl json::Read -> T { … } eod`): a block checks a text
  written in the program; here the text arrives at run time, so there is
  nothing for a block to hold. The typed read needs a type, not a grammar.
* **Reflection at run time** (Go's way): costs a walk of the type at every
  read, and moves to run time a mismatch the build can name.
* **Unknown members ignored by default** (serde, Go, Swift): a renamed member
  becomes a missing one silently - the reason ADR-299 D17 refuses it.

## 6. Consequences

* `T::fields` needs a way to build a value (a reflected field that can be
  given, or a constructor from fields), and ADR-330's type parameter needs
  parsing, before `read[T]` can be written in Nikaia.
* CLAUDE.md's version table gets a row for `packages/`.
