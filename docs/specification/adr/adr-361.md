# ADR-361: A Loop Is a Problem in Horn Clauses; the Compiler Finds Its Invariant With a Growing Portfolio of Strategies, Checks Every One, and Takes Proposals From Outside Programs, an LLM Among Them, Only to Check Them

**Status:** Accepted
**Date:** October 17, 2026

## 1. Question

```nika
fn main(a: int) {
   assert(a > 0)
   assert(a <= 10)
   let mut i = 0
   let mut total = 0
   while i < a {
      i = i + 1
      total = total + 10
   }
   let b = 4 * example(a) + total
   assert(b > 40)
   assert(b < 181)
}
```

After the loop `i == a` and `total == 10 * a`, so `b` lies between 54 and 180.
The prover reads only names that do not change (ADR-269 D9), and ADR-269 D16
stops at a loop that changes a name a claim reads, so both claims are checks at
run time. Carrying a claim through a loop needs an invariant. Who supplies it -
the author, the compiler, or a tool beside it - and how, is the question.

## 2. How others do it

| Method | Tools | Strength | Weakness |
| :--- | :--- | :--- | :--- |
| A written invariant | Dafny, Wuffs, Frama-C WP, Why3 | exact, readable | the author writes and maintains it for every loop |
| Unrolling a short loop | SPARK (a `for` of at most 20 turns), CBMC, Kani | nothing to write | its cost grows with the turns; it stops at a limit |
| Closed forms of recurrences | LLVM's scalar evolution, Aligator | exact and cheap for counters and sums | only those |
| Abstract interpretation | Astrée, Frama-C EVA, IKOS, Clousot | always ends; a fact for every loop with nothing written | not directed at a claim; widening loses precision |
| k-induction | CBMC, ESBMC, Kind 2 | ordinary queries only | weak alone |
| Templates (Farkas) | Colón, Sankaranarayanan and Sipma | complete for the form chosen | the form is chosen in advance |
| Guess and check | Daikon, ICE learning, LLM-proposed invariants | strong; candidates from runs or a model | the guess is not deterministic |
| Property-directed reachability (PDR/IC3) on Horn clauses | z3's Spacer, Eldarica, Golem; SeaHorn, JayHorn, RustHorn translate programs to them | the strongest single method for integers, directed at the claim | large to build; it may search without end; its invariants are hard to read |

Horn clauses (CHC) are the problem these methods share: an unknown relation per
loop head, a clause for entry, one for a turn, one per claim. SMT-LIB writes
them in the logic `HORN`. This table is from memory, not checked against
sources.

## 3. Options

| Option | Example | Why it lost | See |
| :--- | :--- | :--- | :--- |
| Keep today's stop | both claims of §1 checked at run time | the compiler sees every line and proves nothing | D2 |
| Only written invariants | `assert(i <= a && total == 10 * i)` required in the loop | the author proves what the compiler can see; Nikaia does not make the author write what can be found | D3 |
| Only simple counters | `x = x + k` found, nothing else | the prover is meant to grow strong, not stop at the first easy case | D5 |
| One method, PDR from the start | Spacer's algorithm in the solver first | the largest piece first, while cheaper ones prove the common loops; it comes when the others are exhausted | D5 |
| Unrolling as the general way | `a <= 10`, so ten copies of the body | its cost follows the turns, not the claim; kept for special cases in #639 | D5 |
| The loop's form in the frontend | a Nikaia-only walk that knows `while` | another tool using the logic package (ADR-270 D24, #599) would get nothing | D1 |
| An LLM in the build | a model asked during `nikaia build` | a build would depend on a network, a service and chance; ADR-270 D4 and D22 keep a build to what the committed file holds | D6 |
| Trust a proposal | an invariant an LLM gave is used as given | a wrong one would prove a false claim | D4 |
| The compiler calls a service over HTTP | `nikaia prove` posts the problem to an LLM's address | the compiler would carry network code, keys and knowledge of providers that change faster than it does | D6 |
| A `let mut` known only until its first assignment | `x = x + 1; assert(x == 1)` checked at run time | every verifier follows assignments; the prover would stop at the first `+= 1` outside a loop | D9 |
| MCP as the exchange | the proposer is an MCP server | made for LLM tools; a learner from test runs or a foreign solver fits it badly, and an MCP server can stand behind a proposer program | D6 |

## 4. Decision

### D1 — A loop is a problem in Horn clauses, in the logic layer.

The logic layer (ADR-270 D1) states a loop without Nikaia's syntax: its state
names, what holds at entry, its condition, what one turn makes of the names,
each way out, and the goals at points in it or after it. This is the shape of
constrained Horn clauses over the logic's sorts. It is public as the rest of
the logic layer is (ADR-270 D24), and SMT-LIB's `HORN` is its import and export
at the edge (ADR-270 D6). The frontend translates a `while` or a `for` into it,
and the answer back into the program's words (ADR-270 D7). A `break`, a
`continue` or a `return` in the loop is a way out of its own, never folded into
the condition.

### D2 — A claim a loop stands before is asked through the loop, where it is left open.

A claim that reads a name a loop changes, after the loop or inside it, is first
asked as today. Where that leaves it neither proved nor refuted, it is asked
once more through the loop's problem (D1), as ADR-359 D2 asks once more with a
callee's summary. A claim decided without the loop never pays for it. This
replaces the first stop of ADR-269 D16.

### D3 — Nobody has to write an invariant; an `assert` may be one, by the flow, not by its place.

The compiler finds the invariant itself (D5). An `assert` in a loop that reads
names the loop changes is a claim where it stands in the program's flow: it is
proved through the loop, and once proved it is a fact the search may use. What
makes it relate to the loop is which names it reads and how the flow reaches
it, carried back as ADR-269 D15 carries any claim, not whether it stands at the
top of the body.

### D4 — Every invariant used is checked, whoever found it.

An invariant is used only once three ordinary queries (ADR-270 D3) are proved,
each with its certificate (ADR-270 D5): it holds at entry, a turn keeps it, and
it with each way out gives the goal. The invariant is kept in `nikaia.proofs`
with the strategy or the program that found it. Where it came from never
decides whether it is believed.

### D5 — Invariants are found by a portfolio that grows.

The strategy layer (ADR-270 D14) holds the methods and the order they are tried
in, each under the build's counted budget (ADR-270 D25). They are added one by
one:

1. closed forms: a name changed by the same constant on every path of a turn
   is its start plus that constant times the turns taken;
2. abstract interpretation over intervals and octagons;
3. k-induction;
4. guess and check, with candidates from the program's `assert`s and from test
   runs;
5. property-directed reachability (PDR/IC3), when the methods before it are
   exhausted and the solver is ready for it.

A claim none of them proves stays a check at run time; nothing is proved that
the certificate does not show.

### D6 — Outside programs, an LLM among them, may propose invariants; a proposal is only checked.

A **proposer** is a program named in the manifest's `[prove]` table. It is run
only by `nikaia prove --propose`, never by `nikaia build`, `run` or `test`. It
is handed, in a versioned format on its standard input, each loop problem the
build left open, in SMT-LIB `HORN`, with the source of the loop and the names
it reads; it answers with candidate invariants as terms over those names. Each
candidate goes through D4; what passes is written to `nikaia.proofs`, which the
next build reads and `--locked` checks without searching (ADR-270 D22). A wrong
proposal costs time and nothing else. Sending the program's code to a service
outside the machine happens only by that command and that entry, never by
itself. The same interface takes an LLM, a tool that learns from test runs, or
another solver that already does what D5 has not built yet.

**The exchange is a child process and one JSON line per problem, each way**, as
`protoc` plugins and language servers talk to their host. The compiler starts
each proposer once, writes one line per open problem to its standard input -
`{"version": 1, "id": …, "problem": …, "source": …, "names": […]}`, the problem
in SMT-LIB `HORN` - and closes the input after the last; the proposer writes
one line per problem it answers to its standard output -
`{"id": …, "candidates": [ … ]}`, each candidate an SMT-LIB term over the
names - and ends. What it writes to standard error is shown to the user. A
proposer that fails, ends early or writes a line that is not this is one helper
lost: the others and the built-in strategies go on, and nothing is proved by
it. What a provider, a model, a key or a prompt is lives in the proposer, not in
the compiler. `--propose=CMD` names a proposer for one run without the
manifest.

### D7 — The report says what carried a proof through a loop.

`--asserts` names, for a claim proved through a loop, the invariant it used and
where that came from; for one left open, the loop and the names it changes.

### D8 — The order and the criterion.

Built in this order: D1 and D4 with D2; D5's closed forms and intervals with
D7; D6; then octagons, k-induction, guess and check; PDR when D5 says. The first
step is done when §1's two claims are proved, lowering the standalone files and
`std`'s tools costs at most 5 % more instructions, and every invariant used
passed D4.

### D9 — A `let mut` binding is followed through each assignment.

A `let mut` whole-number binding that no call is handed and no lambda or
deferred body changes is a name of the prover from its `let` on, with its
value. An assignment gives it a new value the prover reads as a new name
(`x = x + 1`: the new `x` is the old one plus 1, the static single assignment
form of Dafny, SPARK, CBMC and Kani); after a branch that changes it on one side
or both, it is one side's value or the other's, as the branch it took says;
what a loop changes is read through the loop's invariant (D2). Before its first
assignment it is a binding that does not change, as ADR-269 D9 reads one. A
binding handed to a call or changed from a lambda stays outside: another piece
of code could change it while the prover believes a value. A claim decided
without these names never pays for them (D2, ADR-258 D2).

## 5. Reasons

* **The compiler sees the loop; the author should not have to restate it.**
  The direction the owner set for the prover is to find, not to demand.
* **One problem, many methods.** Horn clauses are what every method in §2
  solves; fixing the problem and not the method lets the portfolio grow, and
  lets #599's users and outside solvers speak the same form.
* **Only what is checked counts.** D4 makes the source of an invariant
  irrelevant to soundness, which is what allows an LLM, a heuristic or a
  foreign solver to help at all.
* **A build stays a function of its inputs.** Proposals and free search add to
  `nikaia.proofs`; a build reads it (ADR-270 D4).
* **Cheap first, strongest when ready.** The common loops are counters and
  sums; the methods that prove them end always and cost little.

## 6. Consequences

* **Part III 14.2** reads a `let mut` through its assignments (D9) and a name a loop changes through the loop's invariant
  and says what `--asserts` shows; **13.2** has `nikaia prove --propose`;
  **13.3** the `[prove]` table. ADR-269 D16's first stop and its open item on
  loop invariants point here.
* **What it costs.** The loop's form and its translation; one more query round
  for a claim left open; each strategy as it is added; a proposer's format.
* **What it risks.** A wrong translation of a loop into clauses would ask the
  wrong question - the certificate checks the arithmetic, not the translation,
  as for ADR-359's summaries. The public loop form is a promise to the logic
  package's users and is chosen with that weight.

**Not decided here:** invariants over a list's elements and other quantified
facts; loops in a function's result summary (ADR-359); unrolling for special
cases (#639); which proposers the project ships, if any.
