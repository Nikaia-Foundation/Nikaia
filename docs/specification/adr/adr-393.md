# ADR-393: A Package Becomes a Rust Library — `artifact = "rust-library"` and `[features]` Chosen by Roots

**Status:** Accepted
**Date:** October 29, 2026 (owner's decision), written November 8, 2026
**Answers:** [#978](https://github.com/Nikaia-Foundation/Nikaia/issues/978)
**Related:** Part III 13.3 (the manifest), 13.2 (`nikaia bind`), 15.1 (a C
library), 15.2 (Rust integration); [ADR-286](adr-286.md) D23-D24 (a published
package is the crate `nikaia_<name>`); [ADR-336](adr-336.md) D2 and
[ADR-338](adr-338.md) D2 (the prefix of what the project publishes);
[ADR-yaml-1](adr-yaml-1.md) D10 (the facade crate and `stream` wait on this)

## 1. Question

A package builds into a program or a C library. A Rust program that wants a
Nikaia package, the YAML package's serde_yaml facade first among them, has no
way to depend on it: the lowered Rust exists only inside a Nikaia build. And a
library with several independent parts (a tree, an event stream, a serde
bridge) has no way to let its user take only the part they need, which Rust
users expect from Cargo features.

Two questions follow. What does a package built for Rust look like? And how
does its author name the parts a Rust user can choose, without writing
`#[cfg]` into Nikaia code?

## 2. Options

For the crate:

* **A. A third artifact, `"rust-library"`.** The lowered package is written as
  an ordinary Cargo lib crate.
* **B. Keep the C library only.** A Rust user links the C library through
  `bindgen`. That costs a second boundary, loses every Rust type at it, and
  turns a borrow into a pointer.

For the parts:

* **C. `[features]` in the manifest, each naming roots.** The compiler works
  out what each root reaches and writes the `#[cfg]`.
* **D. `#[cfg(feature = …)]` written in the source, as Rust does.** Each item
  carries its own condition, and the author keeps those conditions true by
  hand. Every forgotten condition is a build that fails for one combination
  of features only.
* **E. One crate per part.** Code the parts share either moves into a further
  crate or is duplicated. The package's structure would follow how it is
  published.

## 3. Decision

A and C.

### D1 - `artifact = "rust-library"` writes the package as an ordinary Rust lib crate.

`nikaia build` writes `Cargo.toml` and `src/` of a lib crate named
`nikaia_<name>` (ADR-286 D23). Its public API is the package's `pub` items,
lowered as they are for a Nikaia program that depends on the package. It
depends on `nikaia-std` and on the package's own dependencies. A Rust crate
uses it as a path dependency now. It is published to crates.io once
`nikaia-std` is (ADR-336 D2). The build writes the crate to
`target/rust-library/nikaia_<name>/` and prints that path. Nothing in it is
written by hand: the next build overwrites it.

### D2 - `[features]` names features, and each feature names roots.

```toml
[features]
default = ["serde"]
tree    = ["yaml::tree"]
stream  = ["yaml::stream"]
serde   = ["yaml::serde"]
```

A root is a module, which stands for all its `pub` items, or one `pub` item
written by its path. `default` lists features; it is the set a Rust user gets
without asking. A `pub` item that no feature's root names or reaches is always
present: it is the **core**. Without `[features]`, everything `pub` is core.

### D3 - What a root reaches comes with it, and the compiler derives everything else.

Every item a root reaches through calls, types, trait implementations and
constants is in that feature. The compiler derives the following and records
it in the ledger (13.5):

* An item that more than one feature reaches is written under
  `#[cfg(any(feature = "a", feature = "b"))]`.
* A feature that reaches all of another feature's roots implies it, and the
  generated `Cargo.toml` lists the implication (`serde = ["tree"]`).
* A dependency that only items under a feature use is written
  `optional = true`, and each feature that reaches it lists `dep:<name>`.

The source holds no condition. The manifest names only the roots.

### D4 - Features only add, and a grammar's streaming form is a feature's.

A feature adds items and never changes or removes one, so any set of features
builds the same code for the items they share. The lowering writes a
grammar's reader form (`parse_<rule>_reader`, `#[stream]`) only where a
feature reaches it with a reader. Without such a feature the crate holds only
the forms over a whole input.

### D5 - Features act on a rust-library build and on `nikaia bind`.

A program has no user who chooses parts, so `[features]` in a package built as
a program is refused. A C library is built whole. `nikaia bind <language>
--features a,b` writes a binding for those features and the core only. The
binding's default is `default`.

### D6 - The compiler checks every feature alone and all of them together.

A rust-library build compiles the crate with the core only, with each feature
alone, and with all features. A combination rustc refuses is reported on the
`.nika` root of the feature that fails, as a Nikaia diagnostic. It is not an
internal compiler error (`NK1343`). This catches what the derivation of D3
missed.

The new codes (Part III C.3):

* `NK1344`: a root that names nothing, or an item that is not `pub`.
* `NK1345`: a feature that does not build alone or together with the others.
* `NK1346`: `[features]`, or `--features`, where the build is a program.
* `NK1347`: a feature list that names an undeclared feature, or a feature
  name Cargo does not accept.

## 4. Consequences

* A Rust program depends on a Nikaia package like on any crate. The YAML
  facade (ADR-yaml-1 D10) becomes hand-written Rust over `nikaia_yaml`.
* An author splits a package into features by naming roots. When code moves,
  the conditions follow it, because the compiler derives them.
* A rust-library build compiles the crate once per feature, plus twice more.
  That costs time and keeps every published combination building.
* The build of this ADR is three steps: the crate (D1), the features (D2-D4,
  D6), and the features in `nikaia bind` (D5).

## 5. What this does not decide

* Where the YAML facade's hand-written Rust lies inside `packages/yaml/`
  (ADR-yaml-1 section 6). That is decided with the facade's own step (#928
  step 8), which is the first user of this ADR.
* How a version of a rust-library crate follows `nikaia-std`'s version. That
  is decided when `nikaia-std` is published.
