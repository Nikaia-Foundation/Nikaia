# ADR-379: An Unconditional Write Is Emitted Before the `if`s Beside It That Cannot Tell

**Status:** Accepted
**Date:** October 22, 2026
**Answers:** whether the compiler may write a statement of a block in another
place than the one it is written in, and when (issue
[#781](https://github.com/Nikaia-Foundation/Nikaia/issues/781))
**Related:** Part I 8.1.1 (statement order is the written order),
[ADR-306](adr-306.md) D18, D19 (a proved check), [ADR-376](adr-376.md)
(`unsafe { assume(…) }`), [ADR-378](adr-378.md) (the emitted code's `unsafe`),
[ADR-377](adr-377.md) (the 1BRC programs)

## 1. Context

A loop that adds a row to a slot reads naturally as

```nika
if v < slot.min { slot.min = v }
if v > slot.max { slot.max = v }
slot.sum += v
slot.count += 1
```

LLVM turns `slot.sum += v` into one instruction that adds into memory only
where the load, the add and the store stand in one basic block. The two `if`s
end that block, so the load is taken before them and the store after: six
instructions where two do, in every turn. The same four lines with the two
writes first cost four instructions a row less, in Rust as in Nikaia; the
Rust that `rustc` gets from Nikaia, with only those lines swapped, counts the
same difference. LLVM's own passes do not move the writes across the
branches, even where the overflow check is already gone; and where it is not,
they could not, not knowing that nothing between can stop the program.

The compiler knows it. It knows which places a statement reads and writes,
that `slot.sum` and `slot.min` are different fields, and which checks are
proved. A programmer should not have to know how a code generator forms its
blocks to write the natural order.

Other compilers: C and Rust compilers move memory writes freely under the
as-if rule where nothing can observe the difference; GCC's and LLVM's store
motion stops at anything that may trap or call out. Java's JIT does the same
with its own knowledge of which operations can throw.

## 2. Decision

### D1 — A write that runs unconditionally is emitted before the `if`s in front of it, where no program can tell.

In a block, a statement `S` that assigns to a place (`p = e`, `p op= e`)
is emitted before an `if` `T` that stands directly in front of it, or in
front of it with only such `if`s between, when all of these hold:

1. `T` neither reads nor writes `p`: every place `T` names differs from `p` in
   a field, or is a local other than `p`'s root;
2. `S` reads nothing `T` writes;
3. neither calls a function that is not pure, does input or output, pauses,
   takes a lock or spawns: `T` and `S` touch only memory;
4. neither `T` nor `S` can stop the program: every check in them (an index,
   an overflow, a division) is proved, and neither holds a `panic`, an
   `assert` or a call that can throw;
5. `T` does not leave: its arms hold only assignments and such `if`s, no
   `break`, `continue`, `return` or `throw`, so `S` runs after it on every
   path, as it does before it.

The block's last statement, its value, is not moved.

Nothing else is moved, and nothing moves past a statement that is not such
an `if`.

**Why this is the written order still (Part I 8.1.1).** A program sees a
statement's effects through what it reads later, through another task, or
through what it leaves when it stops. Condition 1 and 2 keep every read
seeing the value it saw. Condition 3 keeps another task from seeing anything
between the two: it meets this one only at a pause, a lock or a spawn, and
none moves. Condition 5 keeps `S` running exactly when it ran. Condition 4
keeps a stop from falling between them: were one side
able to stop, a `drop` in the teardown or the panic hook could see the other
side's write done or not done, and where both could, which stops first would
change.

### D2 — In every build, the same.

The order is chosen from the program and from what is proved, not from the
build's profile or from `remove-*`: a debug build runs the statements in the
order the release build runs them, so a fault that the order exposes is found
in the debugger. Each statement keeps its own source line; a debugger steps
from the moved write to the `if` before it, as in any optimised code.

### D3 — A test holds where it moves and where it does not.

The emitted order is tested for a case that moves and for each condition of
D1 that keeps a case from moving: the `if` reads `p`; it writes what `e`
reads; one side calls an impure function; one side has a check that is not
proved; the `if` leaves.

## 3. Rejected alternatives

* **Leave it to the program.** The 1BRC programs did it by hand; a program
  written in the natural order loses four instructions a row and nobody
  says why. The compiler has the facts; the programmer should not need
  LLVM's block structure.
* **Compute `min` and `max` without a branch**, so all four writes stand in
  one block: a select costs a load, a compare, a move and a store per field
  where the branch costs a compare against memory and a jump that is almost
  never taken; four instructions a row more than today.
* **Only in release builds**: then the order a fault depends on would differ
  from the one the debugger shows, the worst place for a difference.
* **A general scheduler**, moving any independent statement anywhere: what
  it gains is not measured, and every move costs registers somewhere else.
  This rule moves the one shape that is measured to gain.
* **A new LLVM pass, or a patch to an existing one**: out of this project's
  reach, and LLVM would still lack the facts of condition 4.

## 4. Consequences

* `benches/brc/fast-unsafe.nika` keeps the natural order and gains what the
  hand-swapped order gained.
* A write whose overflow check is not proved does not move: proving more
  (in the 1BRC programs, a field's sum bounded by an `assume`) lets more
  move.
* Every benchmark is counted before and after; a program that loses keeps
  the rule's cost in its table until the rule is narrowed.
