# ADR-327: Shared State After a Panic Is Never Read Half-Changed — Rebuilt Where It Says How — and Every Task and Shared Value Has a Memory Budget in Memory Nikaia Allocates Itself

**Status:** Accepted. D10's cost is still to be measured (§6).
**Date:** October 6, 2026 (#121); D8 rewritten, D9-D10: October 12, 2026 (#490)
**Answers:** what a panic in one task ([ADR-326](adr-326.md) D4) leaves to the
others, and whether one task can exhaust the memory of all
**Related:**
[ADR-326](adr-326.md) (a panic ends its task);
[ADR-321](adr-321.md) D10 (a counting allocator bounds the build-time run);
Part I 6.2-6.3 (`Shared`, `SharedMut`, the four doors), Part II 12.8 (supervision), Part III 15.2 (crossing into Rust)

## 1. Question

**When a task dies while it changes a value other tasks share, what do they
see; and can one task's memory end everyone else's?**

A panic between two changes in an `update` door leaves a value half-changed.
Part III A.2 promises it is poisoned *so no other thread reads state a
half-finished task left behind*; the lock in `std` takes the guard without
looking at the poison. And a task that reads a large upload into a `String`
grows until the process has no memory left.

## 2. How others do it

| | A lock held by a dying task | Memory of one unit of work |
| :--- | :--- | :--- |
| Erlang/Elixir | nothing is shared; the owner's restart starts its state anew | a heap per process; `max_heap_size` ends that process, unset by default; a full machine ends the VM |
| Rust `std` | poisoned; a program usually `unwrap`s, so every later use panics | the global allocator; failure ends the process |
| tokio, parking_lot | not poisoned; the half-changed value is read | as Rust |
| Haskell STM, Clojure refs | changes go to a copy, committed at the end | - |
| Zig | - | every allocation takes an allocator and can fail; `FixedBufferAllocator` returns `OutOfMemory` |

From memory, not checked against a version.

## 3. Options, weighed

| Option | Why it lost |
| :--- | :--- |
| Read through the poison | a wrong value nobody is told about |
| A poisoned value stays poisoned | every task that needs it dies; the server runs and does nothing |
| Every change to a copy, committed at the end | pays on every change, not on the crash; for a large value, a copy per `update` |
| A budget in Rust's global allocator | an allocator may not panic and a refusal ends the process, so the limit could only be soft |
| One account per allocation, recorded beside it | a few bytes and a count on every allocation; a block per account says the same by address |
| Collections that are Rust's own, as today | their memory is the global allocator's, so no budget is hard |
| Every owned value toward Rust a copy the program writes | a copy, and a `.clone()` to write, where the compiler can follow the value to where it was built and build it where Rust wants it |
| The compiler copies where it cannot follow the value | a copy made unseen, at the boundary where copies cost most; a copy is written or refused, never inserted ([ADR-282](adr-282.md) D7) |
| Nikaia's blocks as Rust's global allocator, so that every `Vec` is in one | a crate that keeps a value past its task points into a block that was emptied; a refusal ends the process |
| A block that only moves a pointer forward | a task that runs as long as a connection frees and allocates without end, and would be ended for memory it no longer holds |

## 4. Decision

### D1 — A poisoned value is never read.

A value behind a lock a panicking task held is poisoned; no door opens it as if
nothing happened.

### D2 — Without a way to rebuild it, a door to a poisoned value panics, in the task that opens it.

By [ADR-326](adr-326.md) D4 that ends that task only.

### D3 — A shared value that says how to build it is rebuilt.

*Made precise by [ADR-328](adr-328.md) D9: the policy, a door during a delay, and giving up.*

```nika
let cache = SharedMut::supervised(fn { Cache::load() })
```

The holders keep the same handle; the runtime calls the function again, puts
its result in place of the poisoned content and lifts the poison. How often is
bounded as a supervisor's restarts are (Part II 12.8). The content starts
anew: what must survive a crash belongs in a store with transactions.

### D4 — Nikaia allocates its own memory: `std`'s collections take it from an allocator Nikaia controls, and every such allocation can fail.

`List`, `String` and `Map` stand on collections with an allocator of their own
(`allocator-api2`, `hashbrown`), not on Rust's `Vec` and `String`.

### D5 — Every task, and every shared value, allocates from a block of its own, and the block is its budget.

What a task allocates is the task's; what is allocated inside a door of a
`SharedMut` or in the construction of a `Shared` is that value's. `Shared` is
written in the source (Part I 6.2), so which account pays is known where the
code stands.

### D6 — A full block is a panic in the task, or a poisoned shared value.

A task whose block is full panics where it allocated - outside the allocator,
so it unwinds - and ends ([ADR-326](adr-326.md) D4); its memory goes with it. A
shared value whose block is full is poisoned, and rebuilt where it says how
(D3).

### D7 — How large a block is, an exchangeable strategy decides.

As admission is ([ADR-326](adr-326.md) D2): `std` provides one that derives
budgets from the memory there is and the tasks running; a package may provide
another. No number is configured.

### D8 — Toward Rust, a view crosses free; a list or text handed to a Rust owner crosses as it is where the compiler follows it back to where it was built, and otherwise only by a `.clone()` the program writes.

`&[T]` and `&str` cross without a copy (Part III 15.2). A list or text a
program hands to a Rust API that owns its `Vec<T>` or `String` crosses as it is
wherever the compiler follows it back to where it was built - through locals,
results, the parameters of functions whose every call it sees, and the fields
of values built in the package. The compiler builds it there outside the block,
from the allocator Rust's own collections use, counted against the task's
budget. A value outside every block already - taken from a channel, handed back
by Rust - crosses as it is too. Where the compiler cannot follow the value - a
`pub` function's parameter, a value read out of a shared value - the hand-over
is refused (`NK2506`) and the program writes `.clone()`: a copy is written or
refused, never inserted ([ADR-282](adr-282.md) D7). How far the compiler follows
decides only how often a `.clone()` is asked for, never whether one is made
unseen. The value leaves the budget at the call. A `Vec` or `String` a Rust API
hands back is taken over as it is, outside the block, and counts against the
budget from then on. Memory a Rust crate or a C library allocates and keeps for
itself is the global allocator's and no task's budget.

### D9 — A value that can outlive its task is never in the task's block, so the block is emptied whole when the task ends; from the hand-over it counts against its receiver.

A value the compiler sees can outlive the task - sent on a channel, stored into
a shared value outside its door, handed to Rust to own (D8), the task's result -
is built outside the block, from the global allocator, and counted against the
task while the task holds it. Where the compiler cannot tell, the value is built
outside. Nothing in the block outlives the task, so the block is given back
whole when the task ends, without a walk over what it held.

From the hand-over the value counts against its receiver: the task that takes
it from a channel or joins the task that produced it, or the shared value it is
stored into. A receiver it does not fit is a full block (D6): the task panics
where it takes the value, and the shared value is poisoned.

### D10 — A budget counts what a task holds, not what it has allocated.

Memory a task frees, it can allocate again. A task that runs as long as a
connection, or as the program, frees and allocates without end; a block that
only moved its pointer forward would end it for memory it no longer holds.

## 5. Consequences

* A crash never leaves a half-changed value to be read; a cache that broke, or
  outgrew its budget, starts again instead of ending the process.
* One request's memory ends that request.
* A task's end costs one hand-back of its block, whatever it held.
* A list or text built for a Rust API crosses to it without a copy.
* **What it costs:** `std`'s collections change their ground; a value that can
  outlive its task, or that goes to Rust, is allocated as today and not from the
  block; a hand-over to Rust the compiler cannot follow asks for a written
  `.clone()`; a hand-over between tasks moves the value's count from one budget
  to the other; the content of a rebuilt value is lost; a full machine still ends the process, as it ends the
  BEAM.

## 6. What this does not decide

* **The cost of D10**: a block that gives freed memory back to the task,
  against the block that only moves its pointer, which #490 measured at 41%
  fewer instructions than `malloc` for short tasks. It can be slower, so it is
  measured before it is built.
* **Whether `update` may work on a copy and put it in place at its end**, so
  that a panic inside it leaves the old value and poisons nothing. For a value
  that copies anyway - a number, a struct of numbers - that copy is not one a
  program would have to write (D8); for a list or a text it would be.
