# ADR-367: A Fold Over a Grammar's Input Takes No More Steps Than the Input Has Room For; Its Counters Are Proved From That, Only Where the Input's Length Is Known

**Status:** Accepted
**Date:** October 19, 2026
**Answers:** whether a counter or a sum that a `fold` or `par_fold` keeps can
be proved not to overflow, and from which facts
**Related:** [ADR-285](adr-285.md) D1 (every whole-number operation is
checked), [ADR-306](adr-306.md) D2 (a check is dropped only on a certificate),
[ADR-314](adr-314.md) (what a grammar matched is a fact of the walk),
[ADR-361](adr-361.md) D4 (every invariant used is checked), D6 (a proposal is
only checked), [ADR-366](adr-366.md) D1 (an entry takes text or `Bytes`);
Part II 10.7 (`fold`, `par_fold`), Part III's `optimization` (the facts a proof
reads)

## 1. Question

```nika
grammar Measurements {
    @frame(boundary: "\n")
    rule MEASUREMENT -> Reading =
        name:NAME ";" => temp:TENTHS frame_end { Reading { name, temp } }

    entry rule file -> Summary =
        par_fold(MEASUREMENT, Summary, fn(acc, m) { acc.record(m) }, Summary::merge)
}

impl Stats {
    fn add(ref mut self, temp: i32) {
        self.sum += temp as i64      // checked
        self.count += 1              // checked
    }
    fn merge(ref mut self, other: ref Stats) {
        self.sum += other.sum        // checked
        self.count += other.count    // checked
    }
}
```

The temperature's checks are proved (ADR-314): `|temp| ≤ 999`. The
accumulator's are not, because a sum over a file looks unbounded to the walk:
it does not know how many rows there are. But a fold over a grammar's input
cannot take more steps than the input has bytes, each step consumes at least
what its element rule matches at the least, and the input's length has a
bound. Can the compiler prove the counters from that, and where does the
argument stop holding?

## 2. How others do it

* **SPARK** proves a counter in a loop from a loop invariant written by hand,
  typically `Count <= I` with `I` the loop index, and the index's range.
* **Dafny** and **Why3** do the same with a ghost variable that counts the
  steps, written by the author.
* **Resource analysis** (amortised and potential-based, as in RaML) derives
  how often a step can run from the size of what it consumes; it is where the
  argument below comes from.
* **LLVM** and the **JVM** version a loop: one check before the loop decides
  between a copy without the per-iteration checks and the original. That is
  how a bound that holds only for inputs below a size is used safely.

None of them takes the bound from the platform's address space; a length is a
fact of the value.

## 3. Options

* **A - the input's address space bounds the length.** On x86-64 with 4-level
  paging a user program maps at most 2^47 bytes, and from that both counters
  of §1 fit. It is wrong: with 5-level paging (LA57, supported by Linux, on
  servers since Ice Lake) it is 2^56 bytes, and 2^56 / 5 · 999 ≈ 1.4·10^19 is
  more than an `i64` holds. A compiler for x86-64 does not know which the
  machine runs. Rejected: a wrong bound removes a check that is needed, and an
  overflow then runs on silently into a wrong result.
* **B - the length of the value bounds it.** Part III already reads the length
  of a text, list, map or set whose elements take space as below 2^60. A fold
  over such an input takes fewer than 2^60 steps. A counter that grows by one
  a step fits in every case; a sum that grows by up to 999 a step does not
  (999 · 2^60 / 5 ≈ 2.3·10^20), and needs C.
* **C - B, and a sum checked once before the fold.** Where a field's bound
  depends on the length and does not fit for every length, one comparison of
  the length before the fold chooses a copy of the step and the merge without
  the field's checks, or the checked one as today.
* **D - the author marks the accumulator** (`@bounded`, an annotation, an
  `ensures`). Rejected: the facts are in the program already, and a wrong
  annotation is the failure mode of A in the author's hands.
* **E - a wider accumulator chosen by the compiler** (`i128` for a sum).
  Rejected: it changes the type the author wrote and what it costs.

## 4. Decision

B for every field that fits, C for the rest, both only where the input's
length is known when the fold starts.

### D1 - Each step of a fold consumes at least its element rule's least width.

The **least width** of a rule is the fewest bytes any match of it takes,
read from the grammar: a literal its length, a class one byte (a character of
text takes one to four), a sequence the sum of its elements, an alternative
the least of its branches, `p{m,n}` `m` times `p`'s, `p*` and `p?` nothing,
`dec[T](p)` and `bytes(p)` what `p` takes, a call the callee's, `frame_end`
its boundary's length. A rule that reaches itself is taken at nothing for the
recursive call, which can only make the width smaller. A step that consumed
nothing would repeat forever and is a parse error, so a step takes at least
`max(w, 1)` bytes, with `w` the element rule's least width.

A fold over an input of `len` bytes therefore takes at most `len / max(w, 1)`
steps, and a `par_fold` the same in all its pieces together: the pieces cut
the input, and every frame belongs to exactly one.

### D2 - The input's length is a fact only where it is known when the fold starts.

Every input a grammar reads today is held whole before the parse starts: text
(a `String` or a mapping, ADR-016 D1) or a `Bytes` (ADR-366 D1). Its length is
a value the fold starts with, below 2^60 as every text's and every `Bytes`'.

**A fold over a stream has no such fact.** Should a grammar one day read input
that arrives while it parses (winnow's `Partial`), its length is not known at
the start and has no bound, and D1's step count does not exist there; no proof
of this record applies to it. The compiler carries the distinction now, not
when streams come: the length a fold's proof starts from is taken from the
input's **extent**, which is *known* for every input above and *unbounded* for
anything else, and the code that reads it says so. A new kind of input starts
as unbounded until a record decides otherwise.

### D3 - A field grows by at most a fixed amount a step; that is an invariant, and it is checked.

For each whole-number field of the accumulator's types the walk computes `k`,
the most one step can add to it or take from it, through everything the step
calls: the step's lambda, the methods it calls, the value a map entry hands
it. Every write of the field along one run of the step counts; a write inside
a loop, or one whose amount has no bound, gives no `k`. The initial value
counts as a step's. The merge must leave each such field the sum of the two
partial results' fields, or one of them; any other merge gives no `k`.

From `k` the walk proposes the invariant `|f| ≤ k · steps`, with `steps` the
count of D1 kept beside the accumulator as a ghost: it exists in the proof,
not in the program. Like every invariant it is used only once checked
(ADR-361 D4): the initial value satisfies it, a step keeps it with `steps + 1`,
the merge keeps it with `steps_a + steps_b`. With `steps ≤ len / max(w, 1)` and
`len < 2^60`, the field's check is proved where `k · 2^60 / max(w, 1)` fits its
type. A counter (`k = 1`) fits an `i64` always.

The proof holds for a method only where it runs inside the fold. A method the
step reaches that is also called elsewhere keeps its checks there; D4's copy is
how the fold gets one without them.

### D4 - A bound that does not fit for every length is checked once, before the fold.

Where `k · 2^60 / max(w, 1)` does not fit, but `k · len / max(w, 1)` does for
the lengths below some `L`, the fold is versioned: the entry compares the
input's length with `L` once, and runs a copy of the step and the merge without
the field's checks below it and the checked fold as written above it. 1BRC's
sum (`k = 999`, `w = 5`) fits below about 4.6·10^16 bytes. The copy is the
lowering's; the grammar and the program do not change.

### D5 - Under the same switches as every other proof.

The facts are the walk's at `proving = aggressive` (ADR-314 D4); a check is
written without its overflow test only under `remove-overflow-checks:on`
(Part III), and what is proved does not depend on it.

## 5. Reasons

* The bound comes from the value, not from the machine: a length below 2^60 is
  a fact of every text and `Bytes`, on every platform, where the address space
  is not (option A).
* Nothing is assumed that is not checked. D3's invariant is a proposal like any
  other and goes through ADR-361 D4; D4's comparison runs on every input.
* A wrong proof would be a silent wrong result, the worst failure Part I
  allows; so every case outside D1-D4 keeps its check: a stream, a write in a
  loop, a merge that is not a sum, a method called outside the fold.
* Counters and sums in an aggregation are among the most common whole-number
  code, and every one of them keeps its check today.

## 6. Consequences

* 1BRC loses both of its accumulator's checks, `count` by D3 and `sum` by D4,
  about 2 instructions a row (callgrind, 0.0.1045).
* D3 needs the walk to follow a step through a lambda and a map entry, where a
  result summary stops today (#641); D3 builds its own walk of the step for
  `k`, not a general summary.
* A future streaming input must declare an unbounded extent (D2); the code that
  reads the extent names this record.

## 7. What this does not decide

* A bound on a fold over anything but a grammar's input (a `for` over a list
  has its length already; one over a stream keeps its checks).
* Fields that are not whole numbers, and a `k` that depends on the step's
  input beyond what ADR-314 proves of a binding.
