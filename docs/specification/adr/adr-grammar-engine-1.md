# ADR-grammar-engine-1: winnow-grammar Is Written in Nikaia, in This Repository, and Its Rust Target Is Published on crates.io Under Its Own Names

## 1. Question

Every `grammar` block in Nikaia, the compiler's own grammar first, is lowered
to Rust text `grammar! { .. }`, which winnow-grammar's procedural macro reads a
second time, analyses, checks and turns into parsers over winnow-grammar's
runtime and winnow. The engine is about 20,000 lines of Rust in another
repository, reached by a pinned git revision. A grammar fault surfaces as a
macro or rustc error on generated text, a fix needs a change there and a
revision bump here, and the analysis runs twice: once in `check_grammar.nika`,
once in the macro. **Is the engine written in Nikaia, and if so, where does its
source live and how do Rust users, who use winnow-grammar from crates.io
without Nikaia, keep getting it?**

## 2. How others do it

| Language / tool | Its answer | What it costs there | Source |
| :--- | :--- | :--- | :--- |
| pest | the generator is a Rust procedural macro; its own grammar parser (`pest_meta`) is generated from a pest grammar and the generated Rust is committed | the committed output must be regenerated by hand when the meta grammar changes | from memory, not checked |
| tree-sitter | the generator is one tool, the parser it writes is C, the runtime is C; every language binding wraps the same C | users of a binding never see the generator; a binding is a thin layer per language | from memory, not checked |
| ANTLR | the tool is Java; each target language has a runtime written by hand in that language | a runtime per target to keep in step; behaviour drifts between targets | from memory, not checked |

What transfers: one generator and one runtime, with the language-specific part
a thin layer (tree-sitter), and committed generated output for bootstrapping
(pest). What does not: ANTLR's hand-written runtime per target is the drift
this decision avoids, since the Rust target here is lowered, not rewritten.

## 3. Options, weighed

### Option A — Keep winnow-grammar a Rust crate

Nikaia depends on it by git revision, as today.

### Option B — Write it in Nikaia in its own repository

`keywan-ghadami/winnow-grammar` holds `.nika` sources; Nikaia takes the lowered
crate by revision.

### Option C — Write it in Nikaia in this repository, publish the Rust target

`packages/winnow-grammar/` here; the lowered crates are committed for the
compiler's build and published to crates.io for Rust users.

### Option D — Write it in Nikaia for Nikaia only

The Rust crate stays at 0.2 and is no longer developed.

### Weighed

| | D1 the special case pays | D2 the compiler works | D3 no cost for the common case | D4 consistent with itself | If it is wrong |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **A** | every grammar fault pays a cross-repository fix and a revision bump | the macro re-reads text the compiler already parsed; faults are reported on generated Rust | today's parsers; no change | the one large Rust part of the toolchain outside the self-hosting rule | nothing to undo |
| **B** | the engine's CI needs a pinned Nikaia binary; the compiler waits for a revision bump on every change | as C | as C | split: the compiler and the engine it depends on are built by different revisions of the toolchain | moving the source later is a copy |
| **C** | the Rust user's macro needs a hand-written shell (D3) | one analysis, one code generation; faults reported on the `.nika` source | must match today's parsers by count (D8) | one toolchain revision builds the compiler and its engine | the committed crates keep working; publication can be stopped |
| **D** | Rust users lose the engine's further development | as C | as C | as C | reviving the Rust crate means rewriting it |

C wins on D2 and D4 at the price A does not pay: a shell of hand-written Rust
for the macro. B loses on D4: the compiler and the engine it is built from would
be built by different toolchains. D gives up the Rust users, which the owner
refused.

## 4. Decision

Option C.

### D1 — The engine's source is the Nikaia package `packages/winnow-grammar/` in this repository, with its own version.

Its runtime and its generator are Nikaia. The Rust source in
`keywan-ghadami/winnow-grammar` is replaced by it, not kept beside it; that
repository receives the published Rust target and nothing is developed there.

### D2 — The Rust target keeps winnow-grammar's public API and crates.

Rust users write `grammar! { .. }` with Rust actions as with 0.2. The crate
`winnow-grammar` is the lowered runtime; the crate `winnow-grammar-macros` is
the shell of D3 over the lowered generator. The generator is not published as
a crate of its own.

### D3 — The macro is a shell of hand-written Rust that holds no grammar logic.

It turns the `TokenStream` into text with a table from byte offsets to spans,
calls the generator, parses the generated text back into a `TokenStream`, and
turns the generator's faults into `compile_error!` at the span of their offset.
It is spliced into the crate by ADR-393 D7. It is the only hand-written Rust of
the engine, on the same footing as the YAML package's serde facade.

### D4 — The generator never parses Rust.

Actions, types and expressions in a `grammar!` are balanced token text to the
generator: it copies them into the output and leaves their checking to rustc,
as 0.2 does with the parts it does not analyse. No `syn`, no `quote`.

### D5 — One generator serves both front ends.

The compiler fills the generator's grammar model from its own tree and calls
the same analysis and code generation; `emit_grammar.nika` no longer writes
`grammar! { .. }` text. A fault the analysis finds is a Nikaia diagnostic on the
`.nika` source with an `NK` code, and a `compile_error!` in the macro. The
checks that `check_grammar.nika` and the macro both make today are made once.

### D6 — A Rust target published for Rust users carries the crate name its manifest gives it.

ADR-286 D23's prefix names a Nikaia package published so that Nikaia programs
can depend on it. A Rust target published so that Rust programs can use it is
not that: it keeps the name Rust users know, here `winnow-grammar` and
`winnow-grammar-macros`. `[rust-library]` gains `crate-name = "<name>"` for the
published name and `proc-macro = true` for a procedural-macro crate.

### D7 — The lowered crates are committed, and the compiler takes them by path.

The compiler's build needs the engine before any Nikaia binary exists. So the
lowered crates are committed in this repository and the workspace depends on
them by path, as the Nikaia half of `std` is (ADR-002 D4). CI lowers the package
again and refuses a difference. The git revision dependency ends.

### D8 — The switch is made when the lowered engine passes 0.2's tests at no higher count.

The lowered crates pass winnow-grammar 0.2's test suite, the compiler's tests
and the YAML package's tests, and the compiler's own parse and `benches/yaml`
count no more instructions under callgrind than with 0.2
([`docs/measuring.md`](../../measuring.md)). Until then the compiler keeps the
git dependency. A test of 0.2 that compares a message may change only in the
message's span or wording, never in what it reports.

### D9 — The Rust target carries what it reaches of `nikaia-std` inside it, privately.

The rust-library build copies the items of `nikaia-std` that the package
reaches, by the reachability ADR-393 D3 already derives, into a private module
of the published crate; the crate does not depend on `nikaia-std`. This is
required, not only convenient: `nikaia-std` depends on winnow-grammar, so a
winnow-grammar that depended on `nikaia-std` would be a cycle Cargo refuses. A
type of `nikaia-std` in the public API of a published Rust target is refused,
since two published targets would each carry their own copy and a Rust user
holding both could not pass one's value to the other.

### D10 — The `unsafe` crates the target reaches go into it as private modules; none is published.

The engine is built for the most a parser can do: what the compiler proved is
not checked again (ADR-378), in the published crate as in Nikaia. The crates
under `crates/unsafe/` that the target reaches are copied into it as private
modules, each with its `README`'s argument for every `unsafe`, and Miri runs on
the published crate under both aliasing models as ADR-218 D2 runs it on the
crates. No crate of `crates/unsafe/` is published for this. The hand-written
`unsafe` of winnow-grammar 0.2 (`rt/bytes.rs`) is not carried over: each site is
a proved site of the emitter or a topic of `crates/unsafe/`.

## 5. Consequences

* The engine's faults are found and fixed here, by the rules for the compiler:
  a defect is fixed in the generator, with a test, and no revision bump
  follows.
* The work runs in this order, each step on its own: the runtime first, behind
  the interface the generated code calls today, so nothing generated changes;
  then the generator (reading, analysis, checking, code generation), compared
  against 0.2's output; then the compiler's emitter switches to it (D5); then
  the shell (D3) and the publication (D6).
* The compiler and its engine are built by one revision of the toolchain;
  a language gap the engine meets is a gap of the language, handled by
  `CLAUDE.md`, *A missing form stops the work*.
* A published crate carries copies of `std` and `unsafe` modules: a fix in
  one of them reaches Rust users with the next release of the target.
* The cost: a shell of hand-written Rust in the macro crate, committed lowered
  crates that every change to the package regenerates, and the `unsafe`
  arguments checked once more, on the published crate.

## 6. What this does not decide

* **Whether a Nikaia type can implement a Rust trait the runtime implements
  today**, winnow's `ParserError` for `ParseError` first. Probed first; if Nikaia
  cannot say it, it is a gap of the language and goes to a decision.
* **Whether winnow itself is replaced** by parsers the generator writes over a
  byte cursor of its own. A later question, decided by measurement.
* **The version of the first release written in Nikaia.**
