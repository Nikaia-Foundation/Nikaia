# ADR-353: A Result's Views Point Where the Body Says, and a Viewed Buffer Outlives Its Owner's Name

**Status:** Accepted
**Date:** October 14, 2026
**Answers:** what a result points into when it may view more than one
parameter, and what a caller may do with an argument while it holds such a
result
**Related:**
[ADR-283](adr-283.md) D3 (no implicit copy), D13 (the walk), D23, D24 (the
keep), D25 (changed by D1-D3 here);
[ADR-251](adr-251.md) D4 (the ledger's spelling);
Part I 6.5, 6.6, 6.8; Part III 13.5, C.3

## 1. Question

**Where does a result point when the body can hand back views of two
parameters, and what does that cost the caller?**

```nika
struct Pair { left: ref String, right: ref String }

fn pair(a: ref String, b: ref String) -> Pair {
    return Pair { left: a, right: b }      // each field views one parameter
}

fn longest(a: ref String, b: ref String) -> ref String {
    if a.len() >= b.len() { return a }
    return b                               // one of the two, chosen at run time
}
```

Nikaia promises that nobody writes or reasons about lifetimes: the compiler
reads off the body where a result points (Part I 6.5). A rule that refuses
these functions, or ties every view of a result to every parameter, puts that
reasoning back on the programmer.

## 2. How others do it

All rows are from memory, not checked against a current manual.

| Language | A value viewing several inputs | One of several, at run time | The owner changes while viewed |
| :--- | :--- | :--- | :--- |
| Rust | one lifetime per field if written by hand (`Pair<'a, 'b>`), else one shared | allowed with one written lifetime `'a` over both | refused: the owner is borrowed; a reassignment drops the old value, so it is refused too |
| Swift (lifetime dependencies) | a dependence on several sources | a union of sources | refused while the dependent value lives |
| Mojo (origins) | an origin per value | a union, `ref [a, b]` | refused while the origin is in use |
| C++ | unchecked | unchecked | a dangling reference |
| GC languages | the collector keeps every input alive | same | the old value lives on while referenced |

Every language with checked references accepts the run-time choice. None of
them lets an owner give its value up while it is viewed; a collector does,
by keeping the old value alive, which is what a tether does without one.

## 3. Options, weighed

| Option | Why it lost, or won |
| :--- | :--- |
| Refuse a result that may view two parameters (ADR-283 D25) | the programmer splits the function or copies: the reasoning about where a view points, done by hand |
| One source set for the whole value | sound, but a view taken out of one field keeps every other field's source too: a caller holding `p.left` may not change `b` |
| A source set per view, unions where the body chooses at run time | chosen (D1, D2) |
| Name the sources in the signature, `-> ref(a, b) String` | a lifetime with a parameter's name, the annotation the source never has (Part I 6.5); the ledger keeps the spelling |
| A copy where a caller would conflict | an implicit copy (ADR-283 D3) |
| Refuse every use of an owner while a view of it lives, as Rust does | refuses programs whose data is never in danger: giving a value up moves its buffer, it does not destroy it, where a keep can hold it (D3) |
| Copy-on-write when the owner changes in place | an implicit copy (ADR-283 D3) |

## 4. Decision

### D1 — Each view a result holds has its own sources.

Every view a result holds, the result itself or each view inside it (a
field, an element, a variant's value), points into the parameters its ways out
reach, by ADR-283 D13's walk. The sources are kept per view, not per value:
`pair` hands back a `Pair` whose `left` points into `a` and whose `right`
points into `b`, and a view taken out of `left` points into `a` alone.

### D2 — Where the body chooses at run time, the view points into the union.

A view that may come from one parameter or another, by two ways out or by one
value assigned either, points into each of them: `longest`'s result points
into `a` and `b`. The function is not refused. A trait's method or a function
type, which has no body, hands back a view of the receiver, or else of every
parameter that is a view.

### D3 — A caller may give an argument up while a view of it lives; its buffer moves to the keep.

While a caller uses a view that may point into an argument, the argument's
data stays as it was. Giving the value up is not changing it: a reassignment
of the variable, a move, or the end of its scope moves the old buffer into
the keep of whatever holds the view (ADR-283 D23), and it is freed when the
last such view is gone. No copy is made (ADR-283 D3).

### D4 — Changing an argument's data in place while a view of it may be used is refused, at the change.

A change in place - a method that changes the value, an assignment to a part
of it - of data that a view still to be used may point into is refused with
`NK2305`, at the change. The message names the view, the call that made it,
and the way out of the callee that may hand back that argument; it speaks of
data, never of how long anything lives. The ways out it names: use the view
before the change, or take a copy of it with `.clone()` before the change.

### D5 — The ledger writes each view's sources.

A result that is a view writes its sources in the signature,
`-> ref(a | b) String` (ADR-251 D4). A result that holds views writes each
view's sources by its path, `returns = "left: ref(a), right: ref(b)"`. A caller
reads this and never the body.

## 5. Reasons

* **D1:** the body says where each view points; keeping the answer per view is
  keeping all of it. One set per value would make a caller pay, for every
  view it takes out, the sources of the views it does not hold.
* **D2:** a run-time choice is knowledge the compiler has: the view points
  into one of two, so both stay as they were. ADR-283 D25 refused it because
  the caller met the constraint as a conflict it could not see; D3 removes the
  common conflict and D4 says the remaining one at the caller, naming the
  callee's way out, so the constraint is never unsaid.
* **D3:** a view needs the data, not the variable that named it. A buffer
  that moves into a keep stays where it is; ADR-283 already moves a body's
  buffer and an argument made in the call (D23, D24) this way. Refusing it, as
  Rust does, guards against a destruction that does not happen here.
* **D4:** a change in place is the one case in which a view would see data
  other than what it was given; that is a contradiction in the program, not a
  bookkeeping rule, and it is the only refusal left on this road.
* **D5:** the ledger records what a caller must know about a body it cannot
  see; per view and with unions is what D1 and D2 decide.

## 6. Consequences

* `NK2302` no longer refuses a function for what its result points into; it
  keeps its other cases (a parameter kept where nothing names its buffer).
* `NK2305` is new: a change in place of data a view still to be used may
  point into.
* A buffer may live longer than the variable that named it, while a view of
  it lives: the retention ADR-283 D6 shows in `--tethers`.
* A callee that newly hands back a view of a parameter widens what its callers
  must leave unchanged; the ledger diff shows it (`NK2401`).

## 7. What this does not decide

* Whether `--tethers` or a lint names a buffer kept only because its owner
  moved on.
