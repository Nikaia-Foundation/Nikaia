# ADR-391: The Compiler Derives What It Can and Keeps It — a Private Function's Preconditions From Its Callers, and What a Method Changes From Its Body

**Status:** Accepted
**Date:** November 7, 2026 (supervisor's decision, by the language principles, on the owner's direction that the compiler derives as much as it can itself, in small pieces it stores and reuses)
**Answers:** [#1053](https://github.com/Nikaia-Foundation/Nikaia/issues/1053) (the facts the walk lacks)
**Related:** [ADR-269](adr-269.md) D5 (a precondition is an `assert` at the top), D18 (only what is written is a contract);
[ADR-270](adr-270.md) D19-D22 (`nikaia.proofs`); [ADR-306](adr-306.md) (the walk of the checks);
[ADR-361](adr-361.md) D3, D4, D13 (nobody has to write an invariant; every one used is checked);

## 1. Question

Half the index and arithmetic checks in `tools/*.nika` stay at run time
(#1053: 3049 of 6009 proved on November 7, 2026). The solver is not what
stops them: a new engine added three sites. The facts are missing, and most
of them are in the program already:

* **A parameter no precondition bounds** (274 indexes, 282 operations):

  ```nika
  fn pick(arms: ref Vec[i64], at: i64) -> i64 {
      let mut before = 0
      while before < at {
          sum = arms[before]      // checked: nothing says at <= arms.len()
          before += 1
      }
  }
  ```

  Every caller in the package passes an `at` no larger than `arms.len()`.
  ADR-269 D5 makes the author write `assert(at <= arms.len())` to say it.
* **A fact about one field lost at a call on `mut self`**:

  ```nika
  while r < self.rows.len() {
      self.note(1)               // only writes self.hits
      sum = self.rows[r]         // checked: the call may have changed rows
      r += 1
  }
  ```

  The walk forgets every fact about `self` at the call, because it does not
  know what `note` writes. Its body says so.

The owner's direction (2026-11-07): the programmer writes as little as
possible; the compiler derives what it can, in small pieces, stores what it
derived and uses it again.

## 2. How others do it

* **Frama-C/WP and SPARK** take preconditions from the author; SPARK's flow
  analysis derives `Global` and `Depends` contracts (what a subprogram reads
  and writes) for bodies without them.
* **Infer** (bi-abduction) derives pre- and postconditions per procedure,
  bottom-up over the call graph, and stores them as specs reused by callers;
  an edit re-analyses only the changed procedures and their callers.
* **Whole-program optimisers** (LLVM's IPSCCP, GCC's IPA-VRP) propagate
  argument ranges into internal functions whose every call site they see.

## 3. Decisions

### D1 — A function no other package can call takes, as facts, what all its callers in the package prove about its arguments.

For a function that is not `pub` (or whose package is a program), the walk
gathers at each call site the facts it holds over the arguments, in the
callee's parameter names and their lengths (`at <= arms.len()`,
`0 <= at`), and proposes as the callee's **derived preconditions** the claims
every call site proves. A claim is proposed from the shapes the walk already
reads: a comparison between an argument and a length or a constant at the
call site, and the facts a call site's guard gives. Each is then a fact at the
callee's entry, as a written `assert` at the top is (ADR-269 D5), and an
obligation at every call site, asked like any other claim (ADR-361 D4). A
function taken as a value (a lambda, a function pointer) has call sites the
walk does not see and derives none. A derived precondition is never a
refusal: a caller that does not prove it removes it, and the checks it would
have removed stay.

### D2 — What a function may change is derived from its body.

For every function the walk derives its **frame**: the paths it may write
through its `mut` parameters and `mut self` (a field, a field's length, an
element), by its own assignments and by the frames of what it calls, over the
call graph to a fixed point; a call the walk cannot resolve writes
everything. At a call, the walk forgets only the facts about the paths in the
callee's frame. A frame changes no meaning and no check; it only keeps facts
the walk now throws away.

### D3 — A derived fact is kept, not searched again.

A derived precondition's obligations and a frame's uses are claims like any
other: their answers are kept in `nikaia.proofs` (ADR-270 D19-D22), checked
when read, written by a normal build and compared under `--locked`. The
proposals themselves are cheap and read off the source in each build; what is
kept is what costs, the proofs. An edit to a callee or a caller changes the
claims it asks and so the entries it uses; nothing else is searched again.

### D4 — Derived is not promised.

A derived precondition or frame is never published in the ledger, never
checked when the program runs, and never part of a function's contract
(ADR-269 D18): a `pub` function's preconditions are the ones its author
writes. `--asserts` and `--bounds` show a derived precondition as such, with
the call sites that prove it, so a reader sees what carried a proof.

## 4. Considered and rejected

**Asking the author for an `assert` at the top of every private function.**
It is what ADR-269 D5 offers today and what the owner's direction rules out:
the facts are in the callers already.

**Storing the derived claims themselves in `nikaia.derived`.** That record is
what a package's contract was derived from (ADR-251 D1); a derived
precondition is not a contract, and the proofs that matter are already kept
in `nikaia.proofs`.

**Publishing frames in the ledger for other packages.** Useful later, beside
`touches`, but it widens what a package promises; it waits for a need across
a package boundary.
