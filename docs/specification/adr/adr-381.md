# ADR-381: A Named Property of a Value Is a Fact - `assert(is_sorted(xs))` Is Proved by Name, Carried to the Caller and Checked Once

**Status:** Accepted
**Date:** October 24, 2026
**Answers:** the first step of [#797](https://github.com/Nikaia-Foundation/Nikaia/issues/797),
*how does a program say "this list is sorted" or "this tree is valid", and what
does the compiler do with it?*
**Amends:** [ADR-269](adr-269.md) D9 (what the prover reads)
**Related:** [ADR-269](adr-269.md) D3, D5, D17, D18 (a pure claim; preconditions,
postconditions, the ledger), [ADR-369](adr-369.md) (a struct's rule),
[ADR-306](adr-306.md) D17 (a field is a name while nothing can change it),
[ADR-380](adr-380.md) (not proved is refused unless `warn`)

## 1. Question

```nika
fn is_sorted(v: ref Vec[i64]) -> bool sync { … }

fn first_at_least(v: ref Vec[i64], x: i64) -> i64 sync {
    assert(is_sorted(v))
    …
}
```

The claim is allowed today (its call is pure, ADR-269 D3), but the prover
reads only comparisons of whole numbers: the claim is refused (`NK1300`), or at
`unproved-claims = "warn"` the whole list is walked at every call. It is not a
precondition, so no caller is asked, and nothing after it knows it.

## 2. How others do it

* **Dafny, F\*:** a `predicate` is a function the verifier can unfold; an
  `opaque` one is used by name until revealed. **Liquid Haskell:** measures and
  abstract refinements. **SPARK:** an expression function used in `Pre`/`Post`,
  proved or checked at run time. **Whiley:** a type `sorted` defined by a
  predicate (`type sorted is (int[] xs) where …`). **Eiffel:** a `require` that
  calls a query, checked at run time.
* Common to all: a property gets a **name**, the name is what contracts carry,
  and a call that already has the name owes nothing. Unfolding the body is a
  second, stronger step.

## 3. Decision

### D1 - A pure `bool` call is a name of the prover.

In a claim, a call `p(a, …)` or `a.p(…)` of a `sync` function that returns
`bool`, throws nothing, touches nothing and changes nothing (ADR-269 D3),
whose arguments are names the prover reads or bindings and paths of fields
that nothing can change (ADR-306 D17, D20), is a **property**: a name of its
own, true or false, as `xs.len()` is a whole number of its own. Two
properties are the same name when they call the same function with the same
arguments. The body is not read.

### D2 - Where a property holds, it is a fact.

A property is known after an `assert` of it is reached (proved or checked),
from a precondition at the function's entry, from a callee's postcondition
(`assert(p(result))` at every exit), and from a type's rule (`assert(p(items))`
in a struct, ADR-369 D2) wherever a value of the type is seen. It stops being
known where an argument may change, as a field does (ADR-306 D17).

### D3 - It is a contract like a comparison.

At a function's entry it is a precondition carried to the caller (ADR-269 D5,
D15); the ledger publishes it as written (`requires = "is_sorted(v)"`), with the
callee's package path of `p`. A call proves it when the same property, with the
arguments in place of the parameters, is known there. Not proved, it is
`NK1300`, or at `warn` checked where it stands: at the call, once, so a value
handed down a chain of calls is walked once.

### D4 - What a proof buys in this step.

The property's own check - a call of `p`, as long as the list - is not
emitted where it is proved. Nothing else follows from it: since the body is
not read, it drops no index or overflow check and chooses no algorithm. A
property whose body the prover reads (every element, an order between
neighbours) is a later decision, #798.

## 4. Rejected

* **A new word** (`predicate`, `requires`, a refinement type): ADR-269 decided
  that a written `assert` is the contract; a property is an ordinary function.
* **Unfolding the body now:** a body is a loop or a recursion; reading it needs
  quantifiers or induction (ADR-270's logic is linear arithmetic). That is
  #798's question, and it is not needed to state and carry a property.
* **Trusting a property without the purity rule:** a function that reads the
  world could answer differently at the second call; D1's conditions are what
  make the name stand for one value.

## 5. Consequences

* Part III 14.2, *What the prover reads*, names properties; `--asserts` lists a
  property proved by name as *proved: known from …* (the assert, the
  precondition, the postcondition or the rule it came from).
* **Risk:** a contract is by name, so a changed body of `p` does not change the
  contract's text; NK1208 does not warn of it. The property's meaning is its
  body, as a function's is.
