# Brief: #1045, an untyped let lambda put into a fn field: a call through the field is refused NK2605

Score: compiler bug (b1043's Found, row c), false refusal (NK2605 where nothing can fail); bugs-first default of `docs/priorities.md`. Small, one cause traced.

## Issue #1045 (copied)
Found by b1043 (row c), probed by the architect on the fast binary after 569bb244.

## Problem
```nika
struct H {
    f: fn(i64) -> i64,
}
fn main() {
    let g = fn(x) { x + 1 }
    let h = H { f: g }
    println(f"{h.f(1)}")
}
```
Expected `2`. Got NK2605 "This function can fail, because `H.f` can fail ... with `?`". A false refusal: nothing here can fail.

Rows (all on the same binary):
* a: the program above - NK2605.
* b: `let g = fn(x) { 5 }` (no operator in the body) - NK2605, so the body is not the cause.
* c: `let g: fn(i64) -> i64 = fn(x) { x + 1 }` - runs, `2`.
* d: `H { f: fn(x) { x + 1 } }` inline - runs, `2`.
* e: `let k = h.f` then `k(1)` - runs, `2`.

## Cause (traced)
ADR-351 D1: a `let` bound to code records what the code calls in `stored_code` (`check_core_stmt.nika:606-611`, `check_core_stmt_let`), but only when the bound type `holds_code`; an untyped lambda that no call hands on (#997's look-ahead `check_core_stmt_handed_to` only sees call arguments, :1866) is not `Ty::Fn` there, so the frame is popped and nothing is recorded. The field then gets the name `g` (`check_core_places_code_into`, `check_core_places.nika:468-487`): a local with no `stored_code` entry and not a parameter is `unresolved`, which is the `?` of the message.
