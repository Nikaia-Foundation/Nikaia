1BRC study: the Nikaia compiler vs. human vs. AI

The goal
Nikaia's goal is the best code for everything the compiler can see: you write the plain program, and making it fast is the compiler's job. You leave that path only to go close to the hardware, for what the standard library does not offer your special case, or for knowledge about your input no compiler can have. Here is our program for the One Billion Row Challenge. Read it, then look at the numbers.

This is a preliminary comparison and work in progress: it shows where Nikaia stands today, not where it ends. fast.nika is a Nikaia program written for speed with what the standard library offers today. Every row prints the same output, byte for byte; Nikaia keeps UTF-8 and every index and overflow checked or proved. fast-unsafe.nika is the same program with the claims a programmer who knows the input's format vouches for, each written unsafe { assume(…) }: the table's index in range, the name inside the input, the temperature's shape, the number of stations. In a build that removes checks they are believed, and the checks they imply are gone; a false claim there is undefined behaviour, as it is in Rust's unsafe. Built with no check removed, each claim is checked instead.

Counted with callgrind over a million rows, release builds at 16 codegen units, with the same settings on every side (mispredicted branches at x86-64). A count is the work a program does, not time on a clock, and for a program that uses all cores it is the work of all of them. The authors' own builds for this machine use AVX-512, which callgrind cannot run; they are left out until they can be counted on another machine. The automataIA programs are MIT-licensed and copied into the repository; beowolx/fast_1brc has no licence and is fetched at a fixed commit when the benchmark runs. AI variant 1 is an AI assistant's program from one request, AI variant 2 the same assistant's after several rounds, each measured and improved (why two AI variants).

The savings are estimates, not measurements: each check was removed by hand from the generated Rust at version 0.0.1150 and the program counted again. They overlap, so they do not simply add up; removing all of them at once gave 132.0 for fast.nika then, before @inline saved another seven. Each row is counted again when it is built. At x86-64 the safe fast.nika now does 4 % less work than the fastest human-written program and 15 % less than AI variant 2; the unsafe one 14 % less than the human program. At x86-64-v3 the human program is at 91.5, 8 % below fast-unsafe.nika: about 16 of its gain from x86-64 to x86-64-v3 is a hash that collides less once crc32 is there, about 22 code it compiles only for that level, above all a temperature parse that reads two rows in one AVX2 vector. Nikaia has no vector types yet; that is a decision still to take.
