Very fast

1BRC study: the Nikaia compiler vs. human vs. AI

1. What the study asks

The One Billion Row Challenge reads a file of weather readings, one station;temperature a line, and prints each station's minimum, mean and maximum. It is small enough to read in one sitting and hard enough that people have spent months on the fastest answer: the input has to be searched, hashed, parsed and counted with almost nothing wasted.

The study asks three questions of Nikaia, which is pre-alpha:

  • What does the compiler make of a plain program? examples/1brc.nika is written the way the problem reads: a grammar for a line, a fold over the rows. Making it fast is the compiler's job.
  • What does hand-tuned Nikaia reach today? fast.nika uses the same building blocks as the fastest Rust programs, with no unsafe: every index and overflow is proved or checked. fast-unsafe.nika is the same program with the claims about the input written unsafe { assume(…) }, believed rather than checked.
  • Where does the journey go? The gap between the safe and the unsafe program is what the prover still has to learn. Every step it learns moves the safe program, and every other Nikaia program, without a line of them changed.

Along the way the study shows what Rust can do in the hands of a person and of an AI assistant, who leads, and which tricks put each program where it is.

2. Method

Every program prints the same output, byte for byte, for the same million rows. Counted with callgrind (valgrind --tool=callgrind --branch-sim=yes), never timed: a count is the work a program does, and it does not move from one day to the next. For a program that uses all cores it is the work of all of them. Release builds on every side with the same settings, 16 codegen units, at the baseline x86-64 and at x86-64-v3 (AVX2, BMI2). Length in tokens, the same rule for both languages. The full method and every row are in benches/brc.

3. Results
  • Safe Nikaia leads at the baseline. At x86-64, fast.nika does 18 % less work a row than the fastest Rust a person wrote, and 27 % less than the AI assistant's best, with no unsafe, in a ninth of the human program's tokens.
  • Unsafe Nikaia shows what is left to prove. fast-unsafe.nika does 21 % less than the human program. The 3.5 instructions between it and the safe program are checks the prover cannot yet remove.
  • At x86-64-v3 the human program leads, 7 % below unsafe Nikaia and 12 % below safe Nikaia. Section 4 shows why.
  • The plain program is in the field of the human programs: 209 against 208 and 216, in 642 tokens against several thousand, with the whole file checked as UTF-8 and every index and overflow proved or checked.
4. The techniques, and who uses them

Searching the separator a block at a time. All fast programs find the ; by comparing 16 to 64 bytes at once and reading the hits from a bit mask. In Rust that is intrinsics inside unsafe. In Nikaia it is bytes::find_all over a ByteSet: the standard library does the block compare, and each next hit costs one tzcnt and one cleared bit. Used by: fast.nika, fast-unsafe.nika, beowolx, AI variant 2.

A name as two words. The first sixteen bytes of a station's name, read as two 64-bit words, are both its hash and its key; the bytes are compared only for longer names. Nikaia reads them with u64_le from a padded copy of the input's end, so no read can run past it, and the bounds are proved, not trusted. Used by: the three fast programs and AI variant 2.

A temperature from one word, without a branch. The position of the . is found from the word's bits, and the value follows by shifts and one multiply. Used by: all fast programs. beowolx goes further at x86-64-v3: it parses the temperatures of two rows in one AVX2 vector, about 12 instructions a row fewer than ours.

Checks proved instead of made. Nikaia keeps every index and overflow check unless it proves the check cannot fail. The prover carries facts through loops (prove-through-loops, #767), keeps a type's rule as a fact where no method can break it (#714), and bounds an unsigned shift, a sum with a bounded side and a loop through its break. That took fast.nika from 163.6 to 107.5 instructions a row; the program only states, in a few asserts checked once, what it relies on. Used by: every Nikaia program; in the plain one the temperature's and the counter's checks are proved.

Claims the programmer vouches for. unsafe { assume(claim) } states what the input's format guarantees: a name of at most 100 bytes, fewer than 10 000 stations. Built with checks removed, each claim is believed and the checks it implies are gone; built with checks on, each is checked. nikaia check --asserts lists every claim. Used by: fast-unsafe.nika.

The rare path out of the loop. A station's first row copies its name into the table, once a station. Marked @inline(never), that code stays out of the loop that runs once a row, and the loop keeps its values in registers: 6.7 instructions a row. Used by: fast.nika, fast-unsafe.nika.

UTF-8 checked once a name, not once a byte. The fast Nikaia programs read the file as bytes and check a station's name as UTF-8 once, where it is printed. The Rust programs check nothing. The plain Nikaia program checks the whole file, about 10 instructions a row.

Text keys compared by words. Every Nikaia map is the standard library's own type over hashbrown's table. Where its key is text, it hashes the first sixteen bytes inline and compares a key a word at a time, the trick the fast programs write by hand; Rust's &str == calls memcmp every time. Used by: every Nikaia program with a map of text, the plain 1brc.nika among them (222.9 → 208.8 a row).

All cores in one line. The plain program is a grammar and a fold; par_fold cuts the file and merges the pieces, and whether it runs on one core or all of them is one line in nikaia.toml. The human programs write their threads by hand.

What Rust does only at x86-64-v3. beowolx gains 40 instructions a row from x86-64 to x86-64-v3, unsafe Nikaia 6. About 16 of beowolx's 40 come from a hash that collides less once crc32 is there: its baseline build is weak, and the gain recovers from that. About 22 come from code it compiles only for that level (cfg(target_feature)): the two-row AVX2 temperature parse, bzhi to mask the name, an SSE update of the stats. The Nikaia programs have no target-specific code; LLVM alone brings their 6. A two-row parse with Nikaia's own vector types (simd::Fixed[u64, 2]) was measured and costs more than the scalar parse in Nikaia; it waits for a lowering that keeps the lanes in one register.
