Safe, secure, reliable

Safety is more than one check. A program fails when something goes wrong while it runs and nothing handles it, when data from outside is not what it expected, when a part is used outside what it was made for, when a change quietly breaks a rule another part relies on, and when a service it waits for is slow or gone.

Nikaia looks at all five, at compile time wherever it can. For each one this page says what the compiler checks and where the check stops, and every topic has a page with the whole program and the message the compiler gives.

Layer 1

Errors that have to be handled

A file is missing, an index is past the end of a list, a task fails. A program meets states nobody planned for, and what matters is that each is handled where it happens, and that one failing part does not take the rest of the program with it.

Caught at compile time

Errors that go unhandled

Functions declare when they can fail, and what they can fail with is worked out from their bodies. A call that can fail and is neither handled nor declared is refused when the program is built. A task's error arrives where the program waits for the task and is held to the same rule. For a library that nothing describes, Nikaia cannot know every way it fails; a description of the library closes that gap.

fn load() -> String {
    return fs::read_to_string("config.txt", fs::Root::Anywhere)
}
error: This function can fail, because `fs::read_to_string` can fail.

Checked while the program runs

An index past the end, a number that overflows

An index outside a list or an integer that overflows stops the program and names the line, before anything reads or writes memory it does not own. Where the compiler has proved that such a check cannot fail, a build setting leaves it out of the machine code. A division by a constant zero is refused when the program is built. Where the compiler can show that an index is past the end, a number overflows or a divisor is zero for a value the program reaches, the program is refused too.

Caught at compile time

A failure that ends only its task

A panic in a task ends only that task. Whoever waits for it receives task::Crashed as an error to handle, and the rest of the program goes on. The compiler works out which functions can panic, so only a task that can panic is a failure, and the function that starts it says throws, catches the crash or gives the task a fallback, or it is refused. A task that cannot panic asks for nothing. A panic in main ends the program.

Chosen by the compiler

Cleanup on every way out

A file or a connection is cleaned up where the compiler sees its owner end, on a normal return, on an error and on a panic. When the program ends, the cleanups still due run within the cleanup-deadline the build sets, and one the deadline cuts off ends the program with exit status 70 and names the resource. process::exit runs the cleanups on its way out, and a plain catch does not take an error that is meant to end the program. A failed write to standard output is an io::IoError the program handles.

Caught at compile time

A missing value is a case to handle

A value that may be absent has the type T?, and the program handles the absent case before it uses the value. A read from a map through brackets is a T? too, since the key may not be there. A conversion to a narrower number is written as only where the compiler shows the value fits; elsewhere the program writes checked_ and handles the case where it does not, or truncating_ and names the cut.

Layer 3

Contracts kept at every call

A function is written for certain inputs, and a value shared between tasks is meant to change in a certain way. Nikaia lets these rules be written in the code, and checks them when the program is built, so a state the program relies on is not broken unnoticed.

Caught at compile time

Calls that break a function's contract

An expectation written as an assert becomes a contract. A call that breaks it is refused, a promise about a result is available to the callers, and a contract carries across package boundaries. A claim the compiler cannot prove refuses the program too, unless the project asks for it to be checked while the program runs.

fn percent(n: int) -> int {
    assert(n >= 0 && n <= 100)
    return n
}

percent(140)
error: This call breaks `percent`'s precondition `n >= 0 && n <= 100` every time it is reached.

Where the compiler's view ends

Beyond what a compiler sees A file is told apart by a name written in the program; two tasks writing paths worked out while the program runs are not refused.

Beyond what a compiler sees Code in a Rust crate or a C library that starts threads of its own is outside what the compiler can look into. There it does not refuse, and you hand over a copy instead of shared data.

Two tasks changing the same value

Two tasks that change the same balance at once can overwrite each other's update. Nikaia looks at what each task touches and refuses a task that changes a value bound outside it, and two tasks that write the same file, the same lock or standard output, naming what they share. The message shows the way out, which is a value of its own for each task, a SharedMut changed through update, or the two changes in order.

async {
    async fn { balance = balance + 50 }
    async fn { balance = balance - 30 }   // refused: `balance` is bound outside
}

Caught at compile time

A type keeps its rule

An assert written inside a struct is the type's rule. It has to hold after every construction, at the end of every method that changes the value and after every write to a field from outside, proved where the compiler can and checked while the program runs where it cannot. A binding marked immutable is refused if anything reachable from its value can change, so every task that reads it sees the same value.

Caught at compile time

What crosses into C

A call into a C library is written inside unsafe, and what crosses is a view that lives for the call or an opaque handle that a cleanup releases. A lock may go into a task of the program's own, and the compiler refuses it where it would reach code that nothing describes.

Layer 2

The compiler knows where the data comes from

What a request carries, what another program prints or what a person types is not up to your program. Nikaia knows which values come from outside, and asks for them to be checked where they arrive, before the rest of the program relies on them.

Where the compiler's view ends

Beyond what a compiler sees What valid data is depends on your program. The guard says it; the compiler checks that there is one. Who wrote a file or what arrives on standard input is something only the program knows, and it says so with trusted: true where it reads them, and --trust lists each such place.

A guard where the data arrives

A claim about a value from outside, an assert or a function's precondition, is refused until a guard handles the bad case. After the guard the claim is proved. Words on the command line are checked against main's preconditions before the body runs.

let out = process::run("git", ["rev-parse", "HEAD"])
let n: int = out.stdout.len()
assert(n == 41)
error: `n == 41` is a claim about data from outside the program.

Checked at the call

A path stays in its directory

Every function that opens a path takes the directory the name may not leave. A name such as ../../etc/passwd is refused at the call. Where the program writes fs::Root::Anywhere instead, it answers for the name itself, and nikaia build --trust lists the place.

fs::read_to_string(name, fs::Root::Dir("store"))

Chosen by the compiler

Keys an attacker cannot line up

A map whose keys come from the network gets a hash with a random seed, so whoever sends the keys cannot pick ones that all land in the same place and slow the program down. A map filled from data the program trusts keeps a faster hash. --trust shows which map got which.

Chosen by the compiler

Parsers built from a grammar

A format or a protocol is read by a parser the compiler builds from a grammar, and the parser of HTTP requests is one of them. Input that does not match is a parse error at its offset, for the program to handle. The http package's server caps a request's head at 16 KiB and its body at 1 MiB, limits how long it waits for the head, and answers 431, 413 or 408 past those limits.

Checked at the call

Text from outside, matched and inserted

std::regex uses a dialect that matches in time linear in the input, so a hostile input cannot make a match run away. A template escapes every value it inserts, unless the value is marked raw. Bytes become text only through a check that they are valid UTF-8.

Layer 4

Every change held to the rules

More and more changes are made by a model or an agent, often faster than a person can read them closely. Such a change can look right line by line and still break a rule that another part of the program relies on.

In Nikaia those rules are part of the code, such as the assert that states what a function expects, the throws that says it can fail and the directory a path may not leave. The compiler checks every change against all of them on every build, whoever wrote it. A change that calls a function outside its precondition, lets an error through unhandled or starts two tasks that change the same value is refused, and the message says what to write instead, so an agent can fix the code and build again.

Shown on every build

What the compiler relied on

nikaia build --asserts lists every claim of the program and whether it is proved, checked where the data arrives, or checked while the program runs. --trust lists every place where the program vouches for its input itself. A reviewer reads these beside the diff.

$ nikaia build --asserts
  …/src/main.nika:10  assert(n == 41)  proved
Contracts in the guide →
Where the check stops

The rules that are written

The compiler checks the rules the code states. A change that rewrites a rule itself, removes an assert or writes fs::Root::Anywhere, is accepted. It shows in the diff and in the two reports, and that is where a person looks. A rule nobody has written is not checked.

The longer argument →
Shown on every build

A contract change shows in the diff

Every package commits its ledger, nikaia.contracts, which records for each function what it can fail with, whether it can pause or panic and what it touches. A change that alters any of this alters the ledger, so it shows in the diff, and nikaia build --locked fails in CI until the new ledger is committed. The proofs the build relied on are kept in nikaia.proofs beside it, and each is checked again when it is read.

What a dependency can do while you build

A package has no build script, and a C library is linked by naming it. The tools below Nikaia read no configuration from the project, so a checked-out repository cannot plant any. Code that runs at build time reads only a file that the code, a committed list and the command all name, and it stops when it passes its budget of steps or memory.

Layer 5

Steady under load and failure

A service the program depends on gets slow, a connection stops answering, one task uses more than its share. The program should answer in time with what it has, and the trouble should stay with the part that has it.

Caught at compile time

A deadline for every wait

A task started with async(within: d) is cancelled when its time runs out and ends with task::TimedOut, a failure like any other. The compiler asks for it to be handled, and a fallback stands in where the value is needed. The check is that a timeout is handled, not that the time chosen is right.

let price = async(within: 100.millis()) lookup()
    catch { "cached price" }
In depth →
Where the compiler's view ends

Beyond what a compiler sees Whether a program can get stuck cannot be decided for every program. Where the analysis cannot tell, it does not claim the problem is solved.

Tasks that get stuck

A task that pauses while it holds a lock is refused, since everyone who needs that value would wait too, and so is a lock taken while another is held, written in the block or reached through a call. For several locks at once, update_all takes them in one fixed order, so two transfers cannot hold one each and wait for the other.

a.update fn(mut acc) {
    acc.balance -= 30
    time::sleep(5.millis())
}
error: `time::sleep` can pause, but you're holding a lock here.

First part built

A memory budget for every task

Every task gets a memory block of its own. A task that fills it ends with task::OverBudget, and the rest of the program runs on. It is a protection while the program runs, not a proof, and memory a Rust crate or a C library keeps for itself is in no budget.

The block is a fixed 64 KiB for now and counts the lists a task keeps to itself. Text and values a task hands on, and main, still take memory from the whole program.

In depth →
Checked while the program runs

How many run at once

async(limit: n) { … } lets at most n of its tasks run at once, and the others wait, unstarted, in the order they are written. admission: names the strategy that decides when the next one starts, and on a form that starts one task, when that task starts. A limit: on a form that starts one task is refused before the program runs. The same options work on xs.par_iter(), and within: d there makes the walk fail with task::TimedOut once d has run out. net::serve runs each connection in a task of its own, so a client that sends nothing holds up only its own connection, and the HTTP server answers 500 to a request whose handler panics and goes on serving.

Checked while the program runs

State a crash left behind

When a task panics while it is changing a shared value, the value is marked poisoned, and another task that opens it gets a panic of its own instead of a value changed halfway. A value made with SharedMut::supervised says how to build it, and is built again instead. An update of a number, or a door that only reads, works on a copy or changes nothing, so a panic there poisons nothing.

ADR-327 →
Checked while the program runs

Restarting what failed

supervisor::run starts a list of children and restarts one that crashes, by a strategy that restarts the child alone, all the children, or the child and those after it. One failing part is started again instead of taking the service down. A channel holds a fixed number of values, so a producer that runs ahead waits for the consumer instead of filling memory.

ADR-328 →
Checked while the program runs

Clients that send slowly

The HTTP server gives a request's head ten seconds from its first byte, however the client splits it, and asks a body to arrive at 500 bytes a second once two seconds have passed. A client that falls behind gets 408 and its connection closes. Between requests a connection stays open for 75 seconds, and a quiet one is closed after that. Each limit is an option of http::listen, and each read waits with read(within:), so no task waits on a timer.
