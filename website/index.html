For people and AI writing code together

Safe. Fast. Easy to read.
A programming language for software you can rely on.

Software you can rely on, whether a person writes it, a model, or both together. The compiler checks for the mistakes that are easy to miss in review before the program runs, and says where its checks stop.

Nikaia is a programming language for applications: backends, web services, and software that has to be fast and correct at the same time. That is its home.

It also reaches from small scripts down to the hardware, though those areas are still young and come with rough edges.

Nikaia is built around an ambitious goal: safety, performance, and readability without having to trade one for another.

People and AI

When people and AI write code together

More and more code is written with a model, or by an agent that changes a program on its own. Such code reads well, and its mistakes are often the kind review finds hardest: two tasks that change the same value, an error that nobody handles, a call outside what a function expects. Nikaia's compiler looks for these before the program runs, and where it cannot tell what a call touches, as in a Rust crate or a C library, it says so instead of refusing.

Its messages say what is wrong and what to write instead, so an agent can read the error, change the code and build again, and the person reviews a program the compiler has already checked. Very safe

Catch mistakes before they become failures.

Many bugs follow patterns. Nikaia checks for those patterns before they reach your users, and says where it cannot.

Partly checked, why?

Still being built For async tasks the check is being built (#988), and two writes to the same file are not yet told apart from writes to two files.

Beyond what a compiler sees Code in a Rust crate or a C library that starts threads of its own is outside what the compiler can look into. There it does not refuse, and you hand over a copy instead of shared data.

Two tasks changing the same value

Two tasks change the same value at once. One update overwrites the other.

async {
    async fn { balance = balance + 50 }
    async fn { balance = balance - 30 }   // refused: both change `balance`
}

Partly checked, why?

Still being built A lock taken inside another lock by hand is not refused yet, so for several locks using update_all is up to you.

Beyond what a compiler sees Whether a program can get stuck cannot be decided for every program. Where the analysis cannot tell, it does not claim the problem is solved.

Tasks that get stuck

Tasks wait for each other forever, or one holds up everyone.

a.update fn(mut acc) {
    acc.balance -= 30
    time::sleep(5.millis())
}

Caught at compile time

Calls that break a function's contract

A part of the program is called outside what it was told to expect.

    assert(n >= 0 && n <= 100)

}

Compile-time memory management

Memory released where the code shows it

Memory is released at a point you can see in the code, without collector pauses.

You write no free and no lifetimes. The compiler works out when memory can be released, and the release is a point you can see.

Easy to understand

Concise by design.

You write what should happen, and Nikaia works out the technical details other fast languages make you spell out. When something is wrong, it tells you in plain words what to change.

No function colouring

Waiting does not split your code in two

A function that waits for a file or the network is called like any other. No library needs a waiting and a non-waiting version of the same function, and a wait added deep inside leaves every caller as it is. The program waits where it needs the value.

let a = async count_words(first)    // starts at once
let b = async count_words(second)   // runs beside the first
println("both counts have started")
println(f"{a + b} words")           // waits for both

Why Nikaia exists

Good and fast are not opposites. Nikaia is named for Nika, and nik means good.

Where it fits

What Nikaia is built for.

Safety and robustness

Where a failure is expensive

Services that have to keep running and data that has to stay correct. The compiler looks for an error nobody handles, a task nobody waits for and a call outside what a function expects, and shows where its checks stop.

Speed

Where speed counts

Data processing, batch jobs and code that runs long or often. Programs become optimised machine code, release memory without collector pauses and can spread their work over every core.

Both at once

Where both count

Backends and web services under load, where a slow answer and a wrong one both cost something. This is where Nikaia is at home.

Efficiency

Where resources are scarce or expensive

Cloud bills, small machines and energy. A program that does the same work with less processor time and memory needs fewer servers, and memory is released at a point the code shows, without a collector holding on to it.

AI-generated code

Where a model writes the code

Generated code reads well, and its mistakes are often the ones review finds hardest. The compiler checks for them before the program runs, and its messages say what to write instead, so an agent can fix the code and build again.

Concurrency

Where many tasks run at once

Servers, pipelines and programs that wait on files and the network. The compiler refuses two tasks that would change the same value at once, and a function that waits is called like any other.

For compiler builders

Languages and formats

Describe a language or a data format as a grammar and the compiler builds the parser. Nikaia's own compiler is moving into Nikaia, so these tools are tried on a real compiler.

For libraries

One version of each function

A function that waits is called like any other, so a library offers one version of each function for every caller. Contracts state what a function expects and promises, and the compiler checks the calls where it can.

For small tools

Tools that grow

A command-line tool starts with a few lines and builds to a fast program, and the same code keeps working as the tool grows. This area is still young.

Get involved

Build Nikaia with us.

Nikaia is built in the open, and there is room to help at every size: a single fix, a whole issue, or a part of the language you look after.

Pull requests

Send a change

A clearer error message, a missing example, a test or a fix in the compiler. Open a pull request on GitHub and it is reviewed there.

Issues

Fix an open issue

Issues marked ready are decided and say what to build. Pick one, say in the issue that you are on it, and send the fix.

Responsibility

Take on a part of the project

Look after an area of the language, such as concurrency, grammars or the standard library, or take on a role in the governance of the Nikaia Foundation.
