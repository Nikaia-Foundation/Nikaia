The reliable programming language

A statically typed, compiled, type-safe programming language with easy verification.

The compiler catches easy-to-miss mistakes before the program runs.

Good wins.

Safe, secure, reliable

Safety as a whole, in five layers.

A program fails in more than one way. Nikaia looks at five of them, checks at compile time wherever it can, and says for each where its checks stop.

Caught at compile time

Errors that have to be handled

A call that can fail is handled or passed on, or the program is not built. What a function can fail with is worked out from its body, so its signature says throws and not a list of every error. A task that can panic ends alone, and whoever waits for it handles the crash. A division by a constant zero is refused, and so, once it is built, is an index past the end, an overflow or a division by zero that the compiler can show happens.

fn load() -> String {
    return fs::read_to_string("config.txt", fs::Root::Anywhere)
}
error: This function can fail, because `fs::read_to_string` can fail.

Caught at compile time

Input checked where it arrives

A claim about data from outside waits for a guard where the data arrives, a path from outside stays in the directory the call names, and formats are read by parsers built from a grammar.

let out = process::run("git", ["rev-parse", "HEAD"])
let n: int = out.stdout.len()
assert(n == 41)
error: `n == 41` is a claim about data from outside the program.

Caught at compile time

Contracts kept at every call

An assert is a contract, and a call that breaks it is refused. Two tasks that change the same value are refused too.

fn percent(n: int) -> int {
    assert(n >= 0 && n <= 100)
    return n
}

percent(140)
error: This call breaks `percent`'s precondition `n >= 0 && n <= 100` every time it is reached.

Checked on every build

Every change held to the rules

Every change is checked against the rules the code states, whoever wrote it. A change that breaks one is refused, with what to write instead. A change to a rule itself shows in the diff and in the reports. A package runs no script while it is built, and code that runs at build time reads only the files it is allowed to and stops at its budget of steps and memory.

$ nikaia build --asserts
  …/src/main.nika:10  assert(n == 41)  proved

Steady under load and failure

A wait with a deadline has to handle its timeout. A lock held across a pause is refused, and a value a task was changing when it crashed is not read half-changed. A task that fills its memory block ends alone with task::OverBudget, and the tasks beside it run on.

Compile-time memory management

Memory released where the code shows it

Memory is released at a point you can see in the code, without collector pauses.

You write no free and no lifetimes. The compiler works out when memory can be released, and the release is a point you can see.

When you turn it on, the compiler leaves out the index and overflow checks it has proved cannot fail.

Easy to understand

Concise by design.

You write what should happen, and Nikaia works out the technical details other fast languages make you spell out. When something is wrong, it tells you in plain words what to change.

No function colouring

Waiting does not split your code in two

A function that waits for a file or the network is called like any other. No library needs a waiting and a non-waiting version of the same function, and a wait added deep inside leaves every caller as it is. The program waits where it needs the value.

let a = async count_words(first)    // starts at once
let b = async count_words(second)   // runs beside the first
println("both counts have started")
println(f"{a + b} words")           // waits for both

    entry rule expr -> i64 =
        head:term tail:add_tail* { … }

    rule add_tail -> i64 =

Where it fits

What Nikaia is built for.

Safety and robustness

Where a failure is expensive

Services that have to keep running and data that has to stay correct. The compiler looks for an error nobody handles, a task nobody waits for and a call outside what a function expects, and shows where its checks stop.

Speed

Where speed counts

Data processing, batch jobs and code that runs long or often. Programs become optimised machine code, release memory without collector pauses and can spread their work over every core.

Both at once

Where both count

Backends and web services under load, where a slow answer and a wrong one both cost something. This is where Nikaia is at home.

Efficiency

Where resources are scarce or expensive

Cloud bills, small machines and energy. A program that does the same work with less processor time and memory needs fewer servers, and memory is released at a point the code shows, without a collector holding on to it.

AI-generated code

Where a model writes the code

Generated code reads well, and its mistakes are often the ones review finds hardest. The compiler checks for them before the program runs, and its messages say what to write instead, so an agent can fix the code and build again.

Concurrency

Where many tasks run at once

Servers, pipelines and programs that wait on files and the network. The compiler refuses two tasks that would change the same value at once, and a function that waits is called like any other.

For compiler builders

Languages and formats

Describe a language or a data format as a grammar and the compiler builds the parser. Nikaia's own compiler is moving into Nikaia, so these tools are tried on a real compiler.

For libraries

One version of each function

A function that waits is called like any other, so a library offers one version of each function for every caller. Contracts state what a function expects and promises, and the compiler checks the calls where it can.

For small tools

Tools that grow

A command-line tool starts with a few lines and builds to a fast program, and the same code keeps working as the tool grows. This area is still young.

Get involved

Build Nikaia with us.

Pull requests

Send a change

Issues

Responsibility
